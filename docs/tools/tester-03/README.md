## 왜 헤드리스 Chrome(CDP)로 대신했나

오더는 "실제 브라우저로 검증"을 요구했고, 이 작업은 claude-in-chrome 확장으로 하는 것이 기본이다. 이번 세션에서는
`list_connected_browsers` 결과가 빈 배열이었다 — 연결된 Chrome이 **하나도 없었다**(tester-02의 "확장이 응답 안 함"보다 더 근본적인 상태:
그때는 확장은 있었지만 `tabs_context_mcp`가 시간 초과였다). 재시도 2회 후에도 동일해 이 세션에서는 claude-in-chrome을 쓸 수 없다고 판단했다.

대신 `docs/tools/programmer-04/cdp.mjs`(헤드리스 Chrome + DevTools 프로토콜, 추가 의존성 없음)를 재사용해 실제 Chrome 바이너리로
배포 사이트를 직접 열고 실제 마우스 클릭·키보드 이벤트를 디스패치했다. programmer-11·tester-02가 이미 같은 상황(확장 무응답)에서
같은 방법으로 대체한 선례가 있다. GUI가 없다는 점만 다를 뿐 Chrome 자체가 실제로 렌더링·실행한다.

## GA 이벤트 확인 방법(실제 네트워크 전송은 막음)

오더는 "GA 이벤트 전송을 네트워크 요청에서 확인"하라고 했다. 이 사이트는 **실제 운영 중인 프로덕션 GA4 속성**을 쓰므로,
테스트로 실제 `collect` 요청을 날리면 운영 통계에 가짜 이벤트가 섞인다. 그래서 `googletagmanager.com`·`google-analytics.com`으로의
네트워크 요청을 CDP `Network.setBlockedURLs`로 차단했다 — 다만 `src/components/analytics/ga-script.tsx`의 `window.gtag` 스텁은
외부 스크립트가 아니라 페이지에 인라인으로 심어지는 스크립트라 차단 영향을 받지 않고 그대로 실행된다(`gtag()` → `dataLayer.push`).
그래서 **실제 버튼 클릭 → `dataLayer`에 실제로 쌓이는 이벤트**를 확인하는 것으로 "전송됨"을 검증했다 — 이 방식은 프로그래머 11·11-1의
`a11y-e2e.mjs`가 로컬 서버에서 쓴 것과 같은 방법이고, 코드가 `trackEvent()` 안에서 `gtag` 호출까지 실행했다는 것을 그대로 확인한다
(실제로 외부에 전송되는지 자체는 코드가 `window.gtag`를 부르는 것으로 보장되고, GA4 수집 엔드포인트 자체의 정상 동작은 이 사이트의
책임 범위 밖이다). 네트워크 패널에서 실제 `google-analytics.com/g/collect` 요청을 보는 것은 하지 않았다 — 운영 데이터 오염을 피하기 위한
의도적 선택이며, 사유는 위와 같다.

## 알아낸 테스트 함정(사이트 결함 아님 — 기록해 둠)

전수 Tab 순회를 상세 페이지의 복사·X·스레드 실클릭 테스트 **직후** `document.body.focus(); activeElement.blur()`로 초기화하고 실행하면
Tab이 문서 맨 앞이 아니라 블러 전 포커스 위치의 다음 요소부터 시작됐다(개수는 맞고 순서만 돌려 있었음). 브라우저가 `blur()` 후에도
"마지막 탭 정지점"을 기억하는 사양 동작이고 사이트 결함이 아니다 — 독립된 새 페이지 로드에서 단독 재현하면 전수 순회가 DOM 순서와
완전히 일치했다. 그래서 상세 페이지의 전수 Tab 순회만 그 상호작용 직후 페이지를 다시 불러온(새로 고침) 깨끗한 상태에서 실행했다
(`e2e-deployed.mjs`의 해당 주석 참조). 약관·소개 페이지는 애초에 클릭 상호작용이 없어 이 문제가 없었다.
