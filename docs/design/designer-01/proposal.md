## 0. 도구 제약 (먼저 밝힘)

`mcp__claude-in-chrome__resize_window`가 이 세션에서 **실제로 뷰포트 폭을 바꾸지 못했다**(1280px·390px·1920px·2560px 등 여러 값으로 반복 요청했으나 CSS `innerWidth`가 요청값과 무관하게 두 값 중 하나로 고정됨 — 탭 생성 직후 기본 상태 그대로). 재시도 한계(2~3회) 넘겨 더 시도하지 않고, **실제로 확보된 두 고정 뷰포트**로 실측했다:

- **"데스크톱" 측정값 = 실제 CSS 폭 1920px** (요청은 1280px였으나 1920px로 고정 렌더됨 — Tailwind `xl`(1280px) 이상이라 큰 틀에서 데스크톱 레이아웃 검증 목적은 달성)
- **"모바일" 측정값 = 실제 CSS 폭 585px** (요청은 390px였으나 585px로 고정 렌더됨 — Tailwind `sm`(640px) 미만이라 모바일 분기 검증 목적은 달성, 단 정확히 390px은 아님 → **확인 필요**)

두 값 모두 `window.matchMedia`로 직접 재확인(585px: sm/md/lg/xl 전부 불일치 → 모바일 분기 · 1920px: 전부 일치 → 데스크톱 분기). DPR 2.

## 2. 시안 3개

공통 전제: 사이트 기존 톤(흑백, `Badge` 컴포넌트, Tailwind 토큰 `--border`·`--surface-strong`·`--muted-foreground`·`--ring`) 유지. 새 라이브러리 없음. 목업은 순수 HTML/CSS/바닐라 JS로 같은 시각 언어를 재현했다(`docs/design/designer-01/mockup-*.html`, 이 폴더 안에서만 열리는 단독 파일).

### 시안 A — 상위 12개만 노출 + "전체 태그 보기" → 신규 `/tags` 페이지
`mockup-a-top-n-tags-page.html`

| 항목 | 내용 |
|---|---|
| 노출 개수·근거 | **12개** — "10건 이상"이 자연스러운 1차 임계값(실측 §1-1). 데스크톱·모바일 공통 고정 개수, `flex-wrap`으로 줄 수만 달라짐 |
| 모바일/데스크톱 | 동일 마크업, 폭에 따라 자동 줄바꿈(기존 방식 그대로, 개수만 297→12) |
| 접근성 | 기존 `TagNav` 구조·`aria-current`·`sr-only "게시물 N건"` 그대로 유지. 새 링크 "전체 태그 보기 (297개)"에 명확한 텍스트/`aria-label`. `/tags`는 통상적 페이지라 스크린리더 탐색에 추가 부담 없음 |
| SEO | 메인에서 `/tag/{slug}`로 가는 내부링크는 12개로 줄지만, 신규 `/tags` 허브 페이지가 **297개 전부**에 링크 — 전체 내부링크 그래프는 보존·오히려 구조화(사이트맵에도 `/tags` 추가 가능) |
| SSG | `getAllTags()` 그대로 재사용. `/tags/page.tsx` 1개만 추가되는 완전 정적 라우트. 서버 데이터 의존 없음 |
| 구현 범위 | 신규 라우트 1개(`src/app/(ko)/tags/page.tsx`) + `TagNav` 소폭 수정(`slice(0, 12)` + 링크 1개 추가). `/tag/[slug]`에도 같은 상한 적용할지는 프로그래머 판단 필요 |

### 시안 B — 한 줄 가로 스크롤 칩 + 펼치기 버튼
`mockup-b-scroll-chips.html`

| 항목 | 내용 |
|---|---|
| 노출 개수·근거 | 고정 개수 없음 — 가로 한 줄에 들어가는 만큼(뷰포트 폭에 비례, 1920px 실측 약 9개/585px 약 4~5개 보임). "펼치기"로 전체 |
| 모바일/데스크톱 | 모바일에서는 피드 앱에 흔한 패턴이라 자연스러우나, **데스크톱은 마우스 휠이 기본 세로 스크롤**이라 가로 스크롤 가능 영역임을 못 알아챌 위험 — 우측 페이드 그라디언트만으론 약함, 화살표 버튼 등 추가 신호 필요 |
| 접근성 | 네이티브 `overflow-x:auto`는 **키보드 포커스가 들어가지 않아** `tabindex="0"` + 좌우 화살표 키 핸들러를 별도 구현해야 함(목업에 반영). 펼치기 버튼 `aria-expanded` 필요. A/C보다 접근성 구현 난도·테스트 범위가 큼 |
| SEO | 접힘 상태에서도 297개 링크 전부 DOM에 존재(CSS `display` 토글만) → 크롤러는 전부 수집. 사용자에게는 숨겨진 상태지만 콘텐츠 자체를 숨기는 cloaking은 아님(같은 내용, 표시 여부만 다름) |
| SSG | 전부 클라이언트 토글(가로 스크롤·펼치기), 정적 생성에 영향 없음. 새 라우트 불필요 |
| 구현 범위 | `TagNav`를 `'use client'`로 전환(현재 서버 컴포넌트 → 상태 필요) 후 내부 로직 추가. 새 라우트 없음 |

## 3. 권고안 — **시안 A**

**이유**
1. **서버 컴포넌트 유지** — `TagNav`를 클라이언트로 바꾸지 않아도 됨. `feed-view.tsx` 주석에 이미 "영어 피드의 RSC 트리를 이전과 같게 유지"하려는 설계 의도가 있어(프로그래머 06), A가 기존 방향과 가장 잘 맞는다.
2. **SEO가 가장 명확함** — 297개 전부로 가는 링크가 `/tags`라는 전용 허브에 모여, "숨겨진 콘텐츠"가 전혀 없는 투명한 구조가 된다. 사이트맵에도 바로 추가할 수 있다.
3. **구현 범위가 가장 작고 예측 가능** — 신규 라우트 1개 + 기존 컴포넌트 한 줄 수준 수정. B·C는 서버→클라이언트 전환과 키보드/스크린리더 처리가 추가로 필요해 리뷰어·테스터 공수가 더 든다.
4. 단점(한 번 더 클릭해야 전체 태그 확인)은 있으나, 사용자 요청이 "간략하고 깔끔하게"이므로 **기본 화면은 적게, 원하면 더 보게** 하는 방향이 요청 취지에 부합한다.

**보류 사항(사용자 결정 필요)**: `/tag/[slug]` 상세 페이지의 `TagNav`에도 똑같이 12개 상한을 적용할지, 아니면 상세 페이지는 전체를 유지할지는 정책 판단이 필요하다 — 확인 필요.

## 4. 참고 — 태그 중복·표기 흔들림 관찰 (실행 금지, 목록만)

DOM에서 297개 태그 문자열을 전수 비교해 발견한 후보. **콘텐츠 수정은 업로더 영역**이므로 여기서는 관찰만 한다.

| 후보 | 비고 |
|---|---|
| `6-25전쟁`(하이픈) / `625전쟁`(숫자만) | **동일 사건으로 추정되는 표기 분리** — 두 태그가 각각 독립 카운트되고 있어 병합하면 상위 태그 순위가 바뀔 수 있음 |
| `지뢰`(11건) / `목함지뢰`(16건) | 오더 예시와 일치. 포괄어/구체어 관계로 완전한 오기는 아니나, 상위 태그 영역에 둘 다 노출되어 사용자가 보기에 혼란 가능 |
| `dmz`·`판문점-usb`·`ebs`·`fta`·`kbs` (소문자 영문 5개) | 한국어 태그 사이에서 표기 스타일만 다름(소문자 약어). `dmz`는 최상위 태그(40건)라 영향이 가장 큼 — 대문자 통일(`DMZ` 등) 여부는 기획 판단 필요 |

(참고: `선관위`/`선관위특검`, `중국`/`중국공산당`, `북한`/`북한군` 등은 포함 관계의 서로 다른 구체 주제로 판단해 중복 후보에서 제외했다.)
