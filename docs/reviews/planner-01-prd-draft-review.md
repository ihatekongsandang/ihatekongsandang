### D1. 운영자 큐레이션 링크에 `rel="nofollow ugc"` 일괄 적용 — 내부 모순 + 스펙 오용 + 출처 존중 원칙 충돌
**위치**: `planning/prd.md` §5.1 L149, §7 보안 L205
**인용**:
- L149: `원문 출처 링크를 카드·상세 모두에 명확히 노출(클릭 시 새 탭, rel="noopener noreferrer nofollow ugc")`
- L205: `외부 링크 rel="noopener noreferrer nofollow ugc" (제보 유입 콘텐츠는 ugc 명시)`

**결함 근거 (3중)**:
1. **내부 모순**: L149는 모든 URL 카드(운영자 큐레이션)에 `ugc`를 붙이고, L205 괄호는 `ugc`가 "제보 유입 콘텐츠" 한정임을 시사한다. 같은 문서가 같은 속성을 두 범위로 규정.
2. **스펙 오용** — Google Search Central「Qualify your outbound links」(https://developers.google.com/search/docs/crawling-indexing/qualify-outbound-links) 원문:
   - `ugc`: "We recommend marking user-generated content (UGC) links, such as comments and forum posts, with the ugc value." → 운영자가 직접 고른 링크는 UGC가 아니다.
   - `nofollow`: "Use the nofollow value when other values don't apply, and you'd rather Google not associate your site with, or crawl the linked page from, your site." → 큐레이션 소식지가 자신이 고른 출처를 "연관되기 싫은 링크"로 표시하는 것은 서비스 정체성과 반대.
   - 편집 링크: "For regular links that you expect Google to fetch and parse without any qualifications, you don't need to add a rel attribute."
3. **출처 존중 원칙(CLAUDE.md 핵심 축 5) 충돌**: 큐레이션 사이트의 출처 표기는 링크 신호(크롤 유도·연관성)를 출처에 돌려주는 것까지 포함하는 것이 통상 관행이다. 여기에 `noreferrer`까지 붙이면 출처 사이트는 이 사이트에서 온 유입을 Referer로 인지할 수 없다(MDN rel/noopener: noopener는 "still providing the Referer HTTP header (unless noreferrer is used as well)"). 출처와의 관계 형성·유입 기여 인지를 스스로 차단한다.
   보안 목적(tabnabbing 방지)은 `noopener`로 충분하고, MDN에 따르면 `target="_blank"`는 현대 브라우저에서 이미 `noopener`와 동일하게 동작한다("Setting target="_blank" ... implicitly provides the same rel behavior as setting rel="noopener"").

**슈퍼바이저 의문에 대한 판정**: 의문 타당. **운영자 링크와 제보·댓글 유입 링크는 구분해야 한다.**
| 링크 출처 | 판정 `rel` | 비고 |
|---|---|---|
| 운영자 큐레이션 원문 링크 (v0.1 URL 카드) | `target="_blank" rel="noopener"` | `nofollow`·`ugc`·`noreferrer` 제외. 명시 `noopener`는 구형 브라우저 대비 무해 |
| 제보(v0.3)·댓글(v0.6) 본문 내 사용자 삽입 링크 | `rel="nofollow ugc noopener"` | 슈퍼바이저 검수 후 게시되는 제보는 게시 시점에 운영자 링크로 전환되므로, "검수 없이 노출되는" 링크(댓글 등)에만 적용 |
| 광고·제휴 링크(현재 없음) | `rel="sponsored"` | 장래 대비 표만 명시 |

⚠️ 위 값은 리뷰어 판정이며 최종 속성 확정은 프로그래머 몫이다. PRD에는 **정책(운영자 링크는 출처 신호를 돌려준다 / UGC 링크는 nofollow ugc)** 을 쓰고, 속성 문자열은 "제안"으로 표기할 것.

### R2. 안정 ID 원칙(§3.1 L84) 보강 — 프로그래머 오해 방지
현재 규정: 변경 금지 + 규칙은 프로그래머 확정. 다음이 빠져 있어 v0.4~v0.6에서 사고가 날 수 있다:
1. `id`는 **frontmatter에 명시적으로 기록**하고 파일명·제목 등 가변 값에서 파생하지 않는다(파일 이름 변경 = id 변경 사고 방지)
2. 삭제·비공개된 게시물의 `id`는 **재사용 금지**(과거 반응·댓글 데이터가 새 게시물에 붙는 사고 방지)
3. 게시물 삭제/비공개 시 후속 데이터(반응·공유수·댓글) 처리 원칙(보존/삭제) — 미결이면 미결로 표기
4. URL 경로(`/post/[id]`, L122)에 그대로 노출되므로 URL-safe 문자셋 요구(한글 허용 여부는 프로그래머 제안)

### R4. v0.3 제보 골조(§5.3·§6) 법적 공백 2건
1. 저작권 동의 문구(L157 `저작권 문제없는 콘텐츠만 제출한다는 동의`)는 **권리 보유 확인**만 담고 **이 사이트에서의 이용 허락**(게시·리사이즈·크롭·공유 카드 생성)이 없다. 제보 사진을 편집·게시하려면 이용 허락 문구가 필요.

### R5. §4.3 하이브리드 피드 근거 보강
- SEO 논거는 사실에 부합: Google「Pagination, incremental page loading, and Search」(https://developers.google.com/search/docs/specialty/ecommerce/pagination-and-incremental-page-loading): "Google's crawlers don't 'click' buttons and generally don't trigger JavaScript functions that require user actions" / "Give each page a unique URL. For example, include a ?page=n query parameter" / "include links from each page to the following page using <a href> tags".
- 따라서 L136의 "`?page=2`로도 접근 가능"만으로는 부족하고, **"더 보기" 컨트롤 자체가 `<a href="?page=n">` 링크여야 한다**는 요구를 명시할 것(JS 버튼이면 크롤러가 따라가지 못함).
- L135 "공유·재방문 지점 특정" 논거는 약함 — 이 서비스의 공유 단위는 상세 페이지(`/post/[id]`)이며 피드 페이지를 공유하는 시나리오는 근거가 없다. SEO 논거만 남기거나 근거를 보강할 것.
