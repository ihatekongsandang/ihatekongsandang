## 1. 서비스 정의

> 사용자 원문: "내가 슈퍼바이저에게 URL이나 사진, 사진&글을 주면 그게 게시되는, 카드 형태 뉴스 소식지 정도의 사이트. 모바일, 웹 모두 지원."

### 용어 정의

| 용어 | 정의 |
|---|---|
| **사용자** | 이 서비스의 소유자·운영자. 콘텐츠(URL·사진·글)를 결정하고 게시를 지시하는 주체. `/about`에서는 익명으로 남는다 |
| **슈퍼바이저** | 사용자의 지시를 받아 게시 파일(`content/posts/*.md`) 작성·커밋·배포를 수행하는 AI 세션(Opus 5). 독립된 운영 인격이 아니라 사용자의 게시 도구 |
| **독자** | 사이트를 열람하는 방문자. v0.1은 로그인·상호작용 없이 열람만 가능 |
| **제보자** | v0.3 이후 URL·사진·글을 제출하는 독자. 제보는 사용자(운영자)의 검수를 거쳐야 게시된다 |

**게시 주체**: 사용자(운영자)가 URL/사진/사진+글을 슈퍼바이저에게 전달 → 슈퍼바이저가 큐레이션·정리하여 게시.

**`/about`에 "게시 파일은 AI 세션이 작성한다"는 사실을 고지할지 여부**: **고지하지 않음**을 기본값으로 채택한다.
- **근거**: ① 위 용어 정의에서 이미 명확히 하듯 게시 결정 주체는 사용자이고 슈퍼바이저는 실행 도구일 뿐이므로 고지 여부가 서비스의 사실관계를 바꾸지 않는다. ② 운영자 익명 원칙과 함께, 게시 도구의 세부 구현(AI 세션 사용 여부)까지 공개하는 것은 정보 전달형 톤에 필요한 정보가 아니다.
- **처리 절차**: 이 기본값을 사용자에게 채택 사실로 고지하고, 사용자가 이견을 밝히면 변경한다.
- ⚠️ **확인 필요**: 「인공지능 발전과 신뢰 기반 조성 등에 관한 기본법」(법령ID 014820, 시행 2026-01-22) 제31조②는 "인공지능사업자는 생성형 인공지능 또는 이를 이용한 제품 또는 서비스를 제공하는 경우 그 결과물이 생성형 인공지능에 의하여 생성되었다는 사실을 표시하여야 한다"고 정한다. 이 사이트가 위 표시 의무 대상에 해당하는지, 해당한다면 슈퍼바이저가 작성하는 요약 보완 문구·캡션 등에 표시가 필요한지는 **법률 자문 대상**이다. "고지하지 않음" 기본값은 이 확인이 끝나기 전의 잠정 값이다.

### 서비스 정의

- **형태**: 카드 피드 기반 소식지 사이트. 개별 게시물은 카드(링크 카드 / 사진 카드 / 사진+글 카드)로 표현
- **소재**: 정치·시사 이슈 큐레이션 전반 — 정책 비판·정치인 발언·논평·안보·간첩 행위·의혹. 사용자가 첫 게시 요청으로 정치인의 SNS 발언(정책 비판)을 전달하면서 확장을 확정했다
- **게시물 스키마**: 🔴 **단일 스키마** — 사건의 진행 단계(의혹·수사·기소·판결 등)를 구분하는 상태 라벨이나, 형사 사건/발언·논평을 구분하는 게시물 종류 필드를 두지 않는다. 모든 게시물은 같은 필드 집합을 쓰고, 사실 확인 단계는 요약 문장과 출처로만 전달한다(§3·§6)
- **v0.1 성격**: 정적 사이트, 열람 전용. 독자는 카드 피드를 보고 클릭해 상세를 확인할 뿐 상호작용(로그인·댓글·반응) 없음
- **v0.3 이후**: 제보자가 URL/사진/글을 보낼 수 있게 되어 콘텐츠 공급원이 사용자 본인 + 독자 제보로 확장

## 2. 타깃 사용자·핵심 가치 가설

### 페르소나 가설 (확정된 소재·톤·독자·운영자 정보 기반)

⚠️ 아래는 §0.5에서 **사용자가 확정한 소재·톤·독자 범주**만을 근거로 한 가설이다. 특정 개인·연령·직업 등 주어지지 않은 세부 인적 정보는 추가하지 않는다.

**P1 — 검색 유입 독자**
- 특정 정치·시사 이슈(형사 사건이든 정치인 발언·정책이든)를 뉴스·SNS에서 접한 뒤, 관련 배경·경과를 검색으로 찾아 이 사이트에 도달
- 필요: 산발적으로 보도되는 정보를 한 곳에서 시간순으로 정리해서 보고 싶음
- 핵심 가치: 원문 링크 신뢰성 + 출처 목록·인용문 표기(§6)로 "이 정보가 어디서 확인된 것인지" 즉시 파악

**P2 — 관심사 커뮤니티 독자**
- 정치·시사 이슈에 지속적 관심을 갖고 재방문하는 독자(소재로부터 추론 — 확정 독자 범주는 "특정 관심사 커뮤니티"이며, 관심사의 구체 내용은 소재에서 자연스럽게 좁힌 것으로 별도로 확인된 사실은 아님)
- 필요: 태그로 관련 사건·이슈를 묶어서 추적, 신규 게시물 빠르게 확인
- 핵심 가치: 카드 피드의 훑어보기 경험(모바일 우선) + 공유(v0.5)로 관심사 커뮤니티 내 확산

### 핵심 가치 제안(USP) 가설
산발적으로 보도되는 정치·시사 이슈(형사 사건·정치인 발언·정책 비판 등)를 **카드형으로 큐레이션**하고, 출처 기반 인용문 표기(§6)로 사실관계를 명확히 구분해 보여주는 소식지. 원문 전재 없이 출처를 존중하며, 익명 운영자가 정보 전달에 집중한다.

### 남은 질문
- 예상 게시 빈도·이미지 볼륨 — 이미지 호스팅(public/R2) 판단, 피드 페이지당 게시물 수(N값), KPI 기준선 설정에 필요.

## 3. 게시물 모델 (콘텐츠 스키마 요구사항)

> 🔴 **단일 스키마 (2026-09-21 사용자 지시로 전면 개정)**: 사건 상태 라벨(`status`)·심급(`courtLevel`)·종결 사유(`closureReason`/`closureNote`)·기소 병기(`priorVerdict`)·상태 이력(`statusHistory[]`)·게시물 종류(`kind`) 필드를 **전부 삭제**한다. 모든 게시물은 같은 필드 집합을 쓴다.
> 구체 스키마(필드명·타입) 확정은 프로그래머 몫이며, `instructions/programmer/03-statement-kind.md`(개정본)의 필드 목록과 정합을 맞췄다.

### 3.1 공통 필드 (모든 게시물)

| 필드(가칭) | 필수 여부 | 설명 |
|---|---|---|
| `id`(슬러그) | 필수 | 게시물 고유 식별자. 🔴 **안정 ID 원칙** — 아래 4개 규칙 |
| `title` | 필수 | 카드·상세 타이틀. URL 유형은 OG 제목 자동 추출값 기본, 수동 override 가능(§6② 단정 문구 금지 규칙 준수) |
| `description` | 필수 | 1~2문장 요약. URL 유형은 OG description 우선, 없으면 슈퍼바이저 작성(원문 문장 그대로 복제 금지). 사진 유형은 캡션 또는 본문 첫 문장 중 선택해 작성. §6②의 인용문 표기 규칙을 따른다 |
| `publishedAt` | 필수 | 발행 시각. 정렬 기준(피드는 최신순, 제안) |
| `sourceType` | 필수 | `url` / `photo` / `photo_text`. 카드 렌더링 분기 기준 |
| `attribution`(출처 표기) | 필수 | URL 유형: 원문 사이트명·링크 / 사진 유형: 촬영자·제공처 또는 "플랫폼명 + 공개 계정명"(SNS 원문인 경우, §5.4) |
| `sources[]` | **조건부** | 유형(언론/수사기관/법원/기타) · 명칭 · URL · 일자. **`sourceType: url`이고 `sourceUrl`이 있으면 0건 허용**(원문 링크 자체가 1차 근거). **`photo`·`photo_text`는 최소 1건 필수**(원문 링크가 없어 출처가 유일한 근거이기 때문). §6①의 허용 출처 기준을 따른다 |
| `tags[]` | 선택 | 카테고리를 두지 않는 v0.1에서 유일한 분류 수단(§4.2) |
| `image` | 선택 | 카드 피드에 노출할 대표 이미지. view 화면 결정(카드=제목+이미지, 없으면 플레이스홀더)과 정합하려면 빌드 필수로 두면 안 된다. URL 유형은 없으면 OG 썸네일(§5.1 처리 정책·`useSourceImage` 스위치 적용)로 대체, 사진 유형은 없으면 첫 번째 이미지로 대체. 둘 다 없으면 플레이스홀더 렌더 |
| `useSourceImage` | 선택, boolean | 원문 OG 썸네일을 대표 이미지로 쓸지 여부. **기본값 `false`**(리뷰어 04 판정 확정 — 원문 썸네일에 식별 정보가 없다고 확인된 경우에만 슈퍼바이저가 게시물별로 `true`로 전환) |
| `speaker` | 선택 | `{ name, affiliation }`. 발언자가 있는 게시물(정치인 발언 등)에 기재. 공인·비공인 표기 규칙은 §6③ |

> **카테고리 필드 없음**: 사용자 확정에 따라 v0.1 스키마에 카테고리 필드를 두지 않는다(§4.2).
> **삭제된 필드 (2026-09-21)**: `status`·`courtLevel`·`closureReason`·`closureNote`·`priorVerdict`·`statusHistory[]`·`kind`·`statementType`·`publicFigure`. 빌드 검증에서 `status`가 존재하면 **오류**로 처리해 옛 파일 잔존을 막는다(§3.3).

#### 🔴 안정 ID 원칙 (v0.4~v0.6의 키)
1. `id`는 v0.4(좋아요/싫어요)·v0.5(공유수)·v0.6(댓글)가 외래키로 사용한다. **한 번 게시된 후 값 변경 금지**
2. `id`는 **frontmatter에 명시적으로 기록**하고, 파일명·제목 등 가변 값에서 파생하지 않는다
3. 삭제·비공개된 게시물의 `id`는 **재사용 금지**. 삭제 시 후속 데이터(반응·공유수·댓글) 보존/삭제 원칙은 v0.4 착수 시점 미결
4. URL 경로(`/post/[id]`)에 그대로 노출되므로 URL-safe 문자셋 요구. 한글 허용 여부는 프로그래머 제안

### 3.2 유형별 필드 (`sourceType`)

**① URL(링크 카드)**
- `sourceUrl`(원문 URL, 필수)
- OG 제목·OG 썸네일·OG 요약 (자동 추출, 수동 override 가능 — 추출 실패 대비). **자동 추출 제목·요약을 override하지 않은 경우 상세 페이지에 "원문 제목/요약(출처 인용)" 라벨을 표시**
- 사이트명(OG `site_name`, 추출 실패 시 슈퍼바이저 수동 입력)

**② 사진**
- `images[]`(이미지 1장 이상)
- **`alt` 텍스트 (필수)** — WCAG 2.2 AA 1.1.1 요건. 빌드 검증 스크립트에서 누락 시 오류 처리
- 캡션(선택)

**③ 사진+글**
- `images[]`(이미지 1장 이상), **`alt` 텍스트 (필수, ②와 동일)**
- 본문 텍스트(마크다운)

### 3.3 슈퍼바이저 작성 편의 요구사항 · 빌드 검증
- frontmatter(YAML) + 본문(마크다운) 조합으로, 슈퍼바이저가 사진 파일만 `public/images/`(또는 R2)에 넣고 frontmatter에 필드를 채우는 수준으로 게시 가능해야 함
- URL 유형은 OG 자동 추출 스크립트/도구가 frontmatter 초안을 생성해주는 것을 프로그래머에게 제안(수동 전량 타이핑 방지)
- 빌드 시 다음을 검증하는 스크립트 필요:
  - 필수 필드 누락(`id`·`title`·`description`·`publishedAt`·`sourceType`·`attribution`)
  - `alt` 누락(사진·사진+글 유형)
  - `sourceType: photo`·`photo_text`인데 `sources[]` 0건
  - 🔴 **`status`·`courtLevel`·`closureReason`·`closureNote`·`priorVerdict`·`statusHistory`·`kind`·`statementType` 필드가 파일에 존재하면 오류**(폐지된 필드의 잔존 방지 — 옛 샘플 파일이 새 스키마로 갱신되지 않은 채 남는 사고를 막는다)
  - `id` 중복

## 4. 정보구조(IA)·핵심 화면

### 4.1 사이트맵 (v0.1, 4화면)

```
/                     — 홈 (카드 피드, 최신순 정렬 제안)
/tag/[slug]           — 태그별 피드
/post/[id]            — 게시물 상세
/about                — 소개 + 출처·저작권 정책 + 정정·삭제 요청 접수(§6④)
```
> `/category/[slug]`는 두지 않는다(사용자 확정 — 카테고리 v0.1 생략). v0.3부터 개인정보처리방침 페이지 추가 필요(§5.3·§7 v0.3 DoD).

### 4.2 카테고리 — v0.1 보류 (태그만 운영)
사용자 확정: **v0.1에서 카테고리를 생략하고 태그만 운영한다.** 게시물이 축적된 후 카테고리 도입을 재검토한다. v0.2 초안에서 제안했던 5개 카테고리는 보류하며, 재도입 시에는 형사 사건·발언·논평을 구분하지 않는 현재 단일 스키마에 맞는 체계로 다시 검토한다.

### 4.3 피드 방식 — 무한스크롤 + "더 보기" 하이브리드 (사용자 확정)
사용자 확정: 무한스크롤 + "더 보기" 하이브리드 채택.
- SEO 요구사항: 크롤러는 버튼 클릭·JS 트리거를 따라가지 않으므로, "더 보기" 컨트롤은 **`<a href="?page=n">` 형태의 실제 링크**여야 한다. 초기 N장 서버 렌더 + 이후 청크는 `?page=n` URL로 접근 가능해야 함
- N값(초기 로드 수)은 프로그래머·디자이너 협의, "게시 빈도·이미지 볼륨" 답변 후 조정(§2 남은 질문)

### 4.4 게시물 상세·view 화면 요구사항 (사용자 확정 반영)
- **카드(피드)**: 제목 + 대표 이미지(없으면 플레이스홀더)만. **배지·라벨 없음. 본문·요약은 펼치지 않는다**
- **카드 클릭 → 상세 페이지 이동**
- **상세 페이지**: 요약(`description`) + 원문 링크(외부 이동 CTA, URL 유형) + 출처 목록(`sources[]`, 있으면 — "배경 보도" 등 관계를 상세에 서술) + 발언자(`speaker`, 있으면 — 공인·비공인 표기는 §6③) + 태그 + "원문 제목/요약(출처 인용)" 라벨(override 안 한 경우)
  - 사진/사진+글: 원본 화질 열람(과도한 압축 지양), 여러 장일 경우 갤러리/스와이프, 본문(사진+글)

## 5. URL 카드 인용·저작권 정책

### 5.1 URL 카드 (인용)
- OG 메타(제목·썸네일·요약)만 추출·표시 — **본문 전재 금지**
- 원문 출처 링크를 카드·상세 모두에 명확히 노출(클릭 시 새 탭)

#### 링크 `rel` 정책 (정책만 규정, 속성 문자열은 "제안")

| 링크 출처 | 정책 | 제안 속성(확정은 프로그래머) |
|---|---|---|
| 사용자(운영자) 큐레이션 원문 링크 | 출처 신호를 돌려준다 — 크롤 유도·연관성 차단하지 않음 | `target="_blank" rel="noopener"` |
| 제보(v0.3)·댓글(v0.6) 본문 내 사용자 삽입 링크 | 서비스와 무관함을 명시(검수 없이 노출되는 UGC — 현 설계상 v0.6 댓글만 해당) | `rel="nofollow ugc noopener"` |
| 광고·제휴 링크(현재 없음) | 장래 대비 | `rel="sponsored"` |

> 근거: 큐레이션 소식지가 자신이 선택한 출처에 `nofollow`·`ugc`를 붙이는 것은 출처 존중 원칙과 어긋나며, `noreferrer`는 출처가 이 사이트발 유입을 인지하지 못하게 한다. 보안 목적(tabnabbing 방지)은 `noopener`만으로 충분하다.

#### OG 썸네일 처리 정책 (선택지·기본값 제시, 법률 판단은 확인 필요)

1. **저장 방식** — **기본값: 핫링크**(원 URL 그대로 참조). 재호스팅은 원 저작물의 복제에 해당해 저작권 리스크가 더 크고, 인용(미리보기) 목적에는 핫링크로 충분하다. ⚠️ **확인 필요**: 핫링크가 국내 저작권법상 "복제"에 해당하지 않는다는 실무 견해는 있으나 확정 판례는 확인하지 못했다.
2. **이 사이트 자체 OG 이미지로의 재사용 여부** — **기본값: 재사용하지 않음**. 소셜 공유 시 자체 로고/플레이스홀더를 사용하고, 원문 썸네일은 카드 내부 미리보기 용도로만 사용(`useSourceImage` 스위치와 연동). 근거: 소재 특성상 원문 썸네일에 특정인 얼굴이 포함될 가능성이 있어 초상권 리스크가 겹친다(§6③ 연동).
3. **추출 실패·원본 삭제 시 플레이스홀더**: §4.4 view 화면 결정과 정합. 핫링크 깨짐 감지 시에도 자동 전환.
4. **원 사이트의 제거 요청 절차**: `/about`에 익명 운영과 양립 가능한 연락 채널(이메일 등) 마련 → 접수 후 사용자(운영자)가 확인해 이미지를 플레이스홀더로 교체 또는 게시물 비공개 → **1차 답변은 영업일 3일 이내, 실제 조치는 확인 즉시**(§6④와 동일 기준)

- 요약이 OG description 없이 추출 불가할 경우 슈퍼바이저가 직접 1~2문장 요약 작성 가능해야 함(단 원문 문장 그대로 복제 금지)

### 5.2 사진 게시물
- 사용자 확정: **슈퍼바이저는 게시 전 사진 저작권 관련 확인 절차를 별도로 두지 않는다.** 사용자가 게시를 요청하는 사진은 본인 촬영/소유 또는 게시 권한을 확보한 것으로 전제하며, 그 책임은 사용자에게 있다.
- 출처·촬영자 표기 필드를 두어 필요 시 기재
- 인물 식별 가능한 사진의 실명·얼굴 노출 기준은 §6③ 편집 정책을 따른다

#### 언론사·방송 저작물 캡처의 유형 제한
- **보도 화면·기사 본문 캡처**는 `photo`/`photo_text` 유형으로 게시할 수 없다. 캡처 이미지 자체가 언론사·방송사의 저작물이며, 이를 "사진 게시물"로 올리면 원문 전재 금지 원칙(§5.1)이 무력화된다. 이 경우 **같은 기사·보도를 `url` 유형(링크 카드)으로 전환**해 게시한다.
- **밈·짤 이미지**의 원 출처가 방송·언론 저작물에서 파생된 경우 위와 동일하게 처리한다(게시 불가, 원 보도를 찾아 `url` 유형으로 전환). 원 출처가 사용자 본인의 창작물이면 `photo` 유형으로 게시 가능하다.

#### 사진 속 인물의 얼굴 처리
- 사용자가 전달한 사진(본인 소유·촬영)에 §6③ 기준 비공인 인물의 얼굴이 식별되는 경우, **모자이크 등 가공 없이는 게시할 수 없다.** 가공(모자이크)은 **사용자 소유 사진에 한해 허용**한다(인용물인 OG 썸네일 등 제3자 이미지는 §6③의 가공 확인 필요 원칙이 적용되어 별개다).
- 슈퍼바이저는 얼굴 식별 시 사용자에게 알리고 게시 여부·가공 방법을 **§6③ 규칙에 따라 제안**한다.

#### 사진만 전달된 경우
사용자 확정: 사용자가 URL·글 없이 **사진만** 전달한 경우, 슈퍼바이저가 다음 절차로 게시물을 만든다 — ① 사진 속 텍스트·장면을 직접 분석 ② 관련 기사·짤·뉴스를 웹 검색 ③ §6①의 허용 출처 확인 ④ 초안 작성 ⑤ 사용자 확인 ⑥ 게시. **허용 출처를 1건도 찾지 못하면 게시하지 않고 사용자에게 보고한다.** 세부 절차는 `docs/supervisor/photo-post-workflow.md`를 따르며, 이 PRD는 원칙만 규정한다:
- 사진 속 텍스트·인물·상황을 **추측하지 않는다** — 검색으로 확인된 것만 서술한다(§6②와 함께 적용)
- 출처가 실제로 확인해 주는 사실까지만 요약한다. 출처가 미달하면 더 보수적인 표현(예: "의혹이 제기됨")을 쓴다
- 커뮤니티·SNS·유튜브 등은 그 자체로 출처가 될 수 없고, 검색을 위한 단서로만 쓴다(§6① 기존 원칙과 동일)

### 5.3 v0.3 제보 대비 사전 설계
- 제보자가 URL/사진/글을 제출할 때 다음 두 가지를 **필수 체크**로 받는다:
  1. **권리 보유 확인**: 제출 콘텐츠가 저작권 문제없는 것임을 확인
  2. **이용 허락**: 위 콘텐츠를 이 사이트에서 게시·리사이즈·크롭·공유 카드 생성 등에 사용하는 것을 허락
- 제보자 연락처(선택) 수집 시 **개인정보 수집·이용 동의**, 보관 기간 고지 필요 → v0.3 착수 전 개인정보처리방침 페이지 게시
- 제보 데이터에 "제보자 동의 여부" 필드를 처음부터 스키마에 넣어야 함

### 5.4 🔴 SNS 원문 인용 범위

> 소재 확장으로 정치인 SNS 발언(인스타그램·X·유튜브 등)이 주요 원문이 되었다. 이런 매체는 OG 메타 자동 추출이 막히는 경우가 많아(예: 인스타그램은 비공개 API로 OG 태그를 제공하지 않음) §5.1의 "OG 메타만 추출·표시" 원칙을 그대로 적용할 수 없다.

- **수동 기재 허용**: OG 추출이 실패하면 슈퍼바이저가 게시자(계정명·소속)·캡션·해시태그·게시일을 페이지 본문에서 직접 확인해 수동으로 기재한다.
- **캡션 인용 범위**: 캡션이 짧은 문구·슬로건 수준(대략 1~2문장)이면 요약(`description`)에 **전문 인용 가능** — 통상적 인용 관행 범위이며, 오히려 발언의 정확한 워딩이 사실관계 확인에 필요하다. 원문과 토씨 하나까지 대조해 그대로 옮긴다. 캡션이 긴 글(에세이형 게시물 등)이면 **요약만 하고 전문 전재는 금지**한다.
- **영상 내용**: 릴스·영상을 슈퍼바이저가 시청할 수 없는 경우, 게시물은 **캡션·자막·설명 텍스트를 기준**으로 작성하며, 상세 페이지에 "캡션 기준으로 정리했으며 영상 전체 내용과 다를 수 있음"을 명시한다.
- **출처(`sources[]`) URL 원칙**: `sources[].url`은 **원 매체(기사를 실제로 작성한 언론사) URL**을 쓴다. 포털(다음·네이트·네이버 등)의 전재 URL은 매체명·기자·등록번호를 오인하게 만들 수 있으므로 원 매체 URL을 확인해 대체하고, 확인하지 못하면 그 출처는 제외한다.
- ⚠️ **확인 필요**: 캡션과 영상 실제 발언이 다를 가능성은 사실 확인 리스크다(§6② 단정 문구 금지와 함께, "캡션에 따르면"과 같은 인용 형태를 권장). 법률 자문 대상은 아니나 편집 원칙으로 상시 유의한다.

## 6. 🔴 편집 정책 — 출처 기반·단정 금지

> CLAUDE.md 핵심 축 6(2026-09-21 개정: 상태 라벨 폐지). 정치·시사 이슈, 특히 범죄 의혹 등 특정인을 향한 서술은 명예훼손(사실적시 포함)·허위사실 리스크가 실재한다. **사건 상태 라벨을 두지 않으므로, 사실 확인 단계는 요약 문장(인용문 표기)과 출처만으로 전달한다.** 본 절은 게시물 종류 구분 없이 모든 게시물에 적용된다.

### ① 허용 출처 요건

- 언론사 보도, 수사기관(검찰·경찰·국가정보원 등) 공식 발표·보도자료, 공개된 법원 판결문 중 **최소 1개 이상**을 `sources[]`에 인용해야 게시 가능(단, `sourceType: url`이고 원문 링크가 있으면 그 원문 링크 자체가 1차 근거이므로 `sources[]` 0건 허용 — §3.1)
- "국회·시민단체 등의 주장"을 근거로 들 수 있으나, **그 주장이 언론 보도를 통해 인용된 경우에 한해 인정**한다(단체·개인의 SNS·성명서를 직접 근거로 삼지 않는다)
- **허용 언론사 기본값** (법령 원문 직접 확인 — 「신문 등의 진흥에 관한 법률」 제2조·제9조): 제9조에 따라 시·도지사에 **등록**된 신문·인터넷신문(제2조 1호·2호 정의 충족), 「뉴스통신진흥에 관한 법률」상 뉴스통신사, 「방송법」상 방송사업자. 미등록 매체·1인 미디어·유튜브는 근거로 불허.
- **등록 여부 조회**: 문화체육관광부 「정기간행물 등록관리시스템」(https://pds.mcst.go.kr/pds/, 2026-09-21 직접 접속 확인 — "제호 검색 서비스"로 지역·제호명·법인명별 등록 현황 조회 가능)에서 확인한다.
- **원 매체 URL 원칙**: `sources[].url`은 포털 전재가 아닌 원 매체 URL을 쓴다(§5.4).
- **출처가 실제로 뒷받침하는 만큼만 서술한다**: 요약 문장은 인용한 출처가 확인해 주는 사실관계까지만 담는다. 출처가 의혹·주장 수준이면 "~라는 의혹이 제기됨"으로, 수사·기소·판결까지 보도됐으면 그 사실 그대로 인용문 형태로 쓴다(② 참조).

### ② 인용문 표기·단정 금지 (라벨 없이 사실 확인 단계 전달)

라벨이 없으므로, **요약(`description`) 문장 자체가 사실 확인 단계를 담아야 한다.** 운영자가 스스로 단정하지 않고, 출처가 보도한 그대로를 인용문 형태로 옮긴다.

| 사건 진행 상황(출처 기준) | 요약 문장 예시 |
|---|---|
| 의혹·주장 단계 | "~라는 의혹이 제기됨(출처: OOO)" |
| 수사 중 | "~로 수사 중인 것으로 보도됨" |
| 기소 | "~로 기소된 것으로 보도됨" |
| 1심·2심 유죄 판결 | "~1심(2심)에서 유죄 판결을 받은 것으로 보도됨" |
| 판결 확정 | "~유죄 판결이 확정된 것으로 보도됨" |
| 무혐의·무죄·공소기각 등 종결 | "~무혐의(무죄) 처분을 받은 것으로 보도됨" |
| 정치인 발언·논평 | "~라고 발언함(캡션에 따르면)" / "~라고 비판함" |

- 법원이 확정하지 않은 죄명·혐의를 운영자가 스스로 붙이는 형용사적 단정 표현 금지(예: "간첩" 같은 죄명을 출처 인용 없이 제목에 쓰지 않는다)
- 발언자의 의도·진의·숨은 목적을 운영자가 단정하지 않는다. "~하려는 속셈이다" 같은 논평형 단정은 금지한다
- 자동 추출값(OG 제목·요약)은 원문 그대로의 출처 인용이므로 이 규칙의 override 대상이 아니다 — 대신 상세 페이지에 "원문 제목/요약(출처 인용)" 라벨을 표시한다

### ③ 실명·얼굴 표기 기준 (라벨 없이 재정의)

- **적용 대상**: 운영자(사용자)가 직접 작성·override하는 제목·요약·본문 문구와 자체 편집 이미지(`useSourceImage=false`로 전환해 대체하는 경우 등)에 적용된다.
- **🔴 공인 예외 (지위 기준)**: 공인은 **지위 기준**으로 정의한다 — 선출직(국회의원·지방의원·단체장 등)·고위 공직자·정당 간부·공공기관장 등 **공적 지위를 가진 인물**을 말한다. 그 인물을 언론이 실명으로 보도한 경우에 **한해**(조건) 실명·얼굴 모두 언론 표기를 따른다. **공적 지위가 없는 인물은 언론이 실명 보도하더라도 공인 예외에 해당하지 않는다.**
  - 판정 앵커(참고): 선출직 = 공직자윤리법 제10조① 정무직 / 고위 공직자 = 고위공직자범죄수사처법 제2조 1호 목록(퇴직자 포함) / 정당 간부 = 당헌상 대표·최고위원·원내대표·사무총장·정책위의장·시·도당위원장 / 공공기관장 = 공공기관의 운영에 관한 법률 제4조 지정 기관의 장. 경계 사례는 **비공인으로(보수적 기본)** 처리한다.
- **비공인 인물의 기본 규칙**: 운영자 작성 문구에서 실명 대신 이니셜(예: "ㄱ씨") 사용, 얼굴은 노출하지 않음(자체 이미지 미사용, `useSourceImage=false`). 단, **출처가 유죄 판결의 확정을 보도한 경우에만** 실명·얼굴 표기를 예외적으로 허용한다(헌법 제27조④·형사소송법 제275조의2 — "유죄 판결이 확정될 때까지 무죄로 추정" 원칙에 근거. 확정 여부는 라벨이 아니라 **인용한 출처가 실제로 무엇을 보도했는지**로 판단한다). 그 외(의혹·수사·기소·1심·2심 등 확정 전 모든 단계)는 이니셜·얼굴 비공개를 유지한다. 미성년자 등은 예외적으로 비공개 유지.
- **발언자(`speaker`)가 있는 게시물**: 발언자가 공인이면 실명·소속 표기, 비공인이면 위 규칙을 준용해 이니셜 처리·얼굴 비공개한다. 비공인 개인의 사적 발언은 공적 사안에 대한 것이라도 **게시 타당성 자체를 신중히 검토**할 것을 권고한다(정보 전달형 톤과 사생활 침해 리스크 사이의 균형 — 기본값은 "비공인 개인의 사적 발언은 원칙적으로 게시하지 않음").
- **사건 진행에 따른 실명 갱신**: 이전에 실명으로 작성된 게시물이 이후 무죄·불기소 등으로 확인되면(⑤ 갱신 규칙 참조), 해당 문구의 실명은 **이니셜로 되돌린다.**
- ⚠️ **확인 필요**: 원문 이미지의 얼굴을 모자이크 처리하는 것(가공)이 인용 범위 내 저작권법상 허용되는지는 법률 확인 필요 — 기본값은 가공하지 않고 `useSourceImage=false`로 대체하는 쪽을 택한다.

### ④ 정정·삭제 요청 접수 절차
- `/about`에 익명 운영과 양립 가능한 연락 채널(이메일 등) 마련
- 접수 → 사용자(운영자)가 원 출처 재확인 → 필요 시 **요약 문장·출처 수정 또는 비공개** 처리
- **처리기한**: **1차 답변은 영업일 3일 이내, 실제 조치는 확인 후 즉시** (법정 의무 아닌 서비스 정책, 사용자 확정 가능)

### ⑤ 사건 진행 시 갱신 규칙 (라벨 대신 요약 문장·출처 갱신)
- 라벨을 갱신하는 대신, **요약(`description`) 문장과 `sources[]`를 갱신**한다(안정 ID 원칙과 일치 — 새 게시물을 만들지 않는다). 예: 최초 "~로 기소된 것으로 보도됨" → 이후 "~1심에서 유죄 판결을 받은 것으로 보도됨"으로 요약 문장을 다시 쓰고, 새 보도를 `sources[]`에 추가한다.
- **게시물은 삭제하지 않고 갱신한다** — 무혐의·무죄 등으로 밝혀진 사건도 요약을 갱신해 그 사실을 반영하고, 게시물 자체는 유지한다(기록 보존과 안정 ID 원칙에 따름). 당사자 요청에 의한 비공개는 ④ 참조, 이 원칙과 별개다.
- 상세 페이지에 갱신 이력을 한 줄 표시한다(예: "2026-XX-XX 갱신: 1심 유죄 판결 보도 반영"). 이전 요약 문장에 실명이 있었고 갱신 후 이니셜로 되돌려야 하는 경우(③ 참조) 그 사실도 함께 기록한다.

## 9. 6대 핵심 축별 적용 방안

### SEO
- 게시물별 `<title>`·meta description(§3.1 `description` 필드)·OG 이미지(§5.1 처리 정책·`useSourceImage` 스위치 적용)
- `sitemap.xml` 자동 생성(빌드 시 `content/posts/` 스캔) → §8에서 GSC·네이버 서치어드바이저에 제출
- JSON-LD: 게시물 상세에 적합한 스키마.org 타입 마크업(구체 타입 선정은 프로그래머 제안 필요 — `NewsArticle`류는 언론사가 아닌 큐레이션 사이트에 적용 시 오해 소지가 있어 신중 검토)
- 태그 페이지도 canonical URL·메타 보유(카테고리 페이지는 v0.1에 없음)
- "더 보기" 링크는 실제 `<a href>`로 구현(§4.3)

### AI 검색 최적화 (GEO)
- 명확한 시맨틱 구조(제목-요약-출처-본문 위계) — LLM이 요약·인용하기 쉬운 구조
- `llms.txt` 도입 제안 — 프로그래머 판단
- 요약 필드(§3.1)를 AI 인용용으로 구조화

### 웹표준·시맨틱·접근성 (WCAG 2.2 AA)
- 사진 게시물 `alt` 텍스트 **필수**(§3.2, 빌드 검증 스크립트로 게이트)
- 카드·상세 모두 키보드 탐색 가능, 포커스 인디케이터 명확
- 색 대비 4.5:1 이상 (디자이너 담당)
- 외부 링크는 시각적으로도 "외부 이동"임을 인지 가능하게(아이콘 등)

### 보안
- 외부 링크 `rel` 정책은 §5.1 표를 따른다
- 마크다운 본문 렌더링 시 XSS 방지(sanitize, 원본 HTML 삽입 금지)
- **CSP 헤더 — `img-src` 정합**: OG 썸네일을 핫링크(§5.1)하면 이미지 출처 도메인이 게시물마다 달라진다. `img-src`를 열거식 화이트리스트로 운영하면 새 출처마다 CSP 배포가 필요해 파일 커밋만으로 게시하는 파이프라인이 깨진다. **`img-src`는 `https:` 범위로 허용하거나(스크립트·프레임은 엄격 유지), 자체 이미지 프록시(재호스팅 아닌 캐시 없는 패스스루)를 경유하는 방식 중 하나를 프로그래머가 선택**해 TECH_STACK.md에 근거와 함께 기록한다. Next.js 이미지 최적화(`remotePatterns`) 정합도 함께 판단한다.

### UX/UI 친화성
- 모바일 우선: 카드 1열, 엄지 도달 영역 고려한 CTA 배치
- 진입 장벽 zero: 모든 버전에서 열람은 로그인 불필요(v0.6 댓글 "작성"만 인증이 필요할 수 있음 — 방식 미결)
- 로딩 속도: 정적 생성(SSG) 기반이므로 Lighthouse 90+ 목표

### 🔴 편집 정책 (출처 기반·단정 금지)
- 상세는 §6 참조. 요약: 모든 게시물은 허용 출처(§6①) 기반으로만 게시하고, 사실 확인 단계를 요약 문장의 인용문 표기(§6②)로 전달하며, 실명·얼굴 표기는 공인 여부와 출처가 보도한 내용에 따라 결정한다(§6③). 운영자 단정 문구를 금지하고, 정정·삭제 요청 절차(§6④)를 상시 운영하며, 사건 진행 시 라벨이 아닌 요약·출처를 갱신한다(§6⑤).

## 부록: 디바이스 대응 방식 — 반응형(Responsive) 확정

사용자 확정: **반응형(Responsive)**.

- 근거: v0.1은 열람 전용 단순 카드 피드 — 모바일·데스크톱 간 기능 차이가 없어 적응형(레이아웃 전면 분기)의 이점이 크지 않음. 반응형 하나의 코드베이스로 그리드 컬럼 수만 브레이크포인트별 조정(모바일 1열 → 태블릿 2열 → 데스크톱 3~4열)이 유지보수 비용 대비 효율적
- **Google 공식 근거 (2026-09-21 직접 WebFetch 확인)**: Google Search Central "Mobile-first indexing best practices" 원문 — *"Google recommends Responsive Web Design because it's the easiest design pattern to implement and maintain."* (https://developers.google.com/search/docs/crawling-indexing/mobile/mobile-sites-mobile-first-indexing)
- 단, v0.3 이후 제보 폼·v0.6 댓글 UI 등 상호작용이 늘면 재검토 여지 있음
