## 1. 서비스 정의

> 사용자 원문: "내가 슈퍼바이저에게 URL이나 사진, 사진&글을 주면 그게 게시되는, 카드 형태 뉴스 소식지 정도의 사이트. 모바일, 웹 모두 지원."

### 용어 정의

| 용어 | 정의 |
|---|---|
| **사용자** | 이 서비스의 소유자·운영자. 콘텐츠(URL·사진·글)를 결정하고 게시를 지시하는 주체. `/about`에서는 익명으로 남는다 |
| **슈퍼바이저** | 사용자의 지시를 받아 게시 파일(`content/posts/*.md`) 작성·커밋·배포를 수행하는 AI 세션(Opus 5). 독립된 운영 인격이 아니라 사용자의 게시 도구 |
| **독자** | 사이트를 열람하는 방문자. v0.1은 로그인·상호작용 없이 열람만 가능 |
| **제보자** | v0.3 이후 URL·사진·글을 제출하는 독자. 제보는 사용자(운영자)의 검수를 거쳐야 게시된다 |

**게시 주체**: 사용자(운영자)가 URL/사진/사진+글을 슈퍼바이저에게 전달 → 슈퍼바이저가 큐레이션·정리하여 게시.

**`/about`에 "게시 파일은 AI 세션이 작성한다"는 사실을 고지할지 여부 (N1 결함 수정)**: **고지하지 않음**을 기본값으로 채택한다. 근거: ① 위 용어 정의에서 이미 명확히 하듯 게시 결정 주체는 사용자이고 슈퍼바이저는 실행 도구일 뿐이므로 고지 여부가 서비스의 사실관계를 바꾸지 않는다. ② 운영자 익명 원칙과 함께, 게시 도구의 세부 구현(AI 세션 사용 여부)까지 공개하는 것은 정보 전달형 톤에 필요한 정보가 아니다. ③ 사용자가 이견을 밝히면 변경한다(R6 취지 — 결정 부담 최소화).

### 서비스 정의

- **형태**: 카드 피드 기반 소식지 사이트. 개별 게시물은 카드(링크 카드 / 사진 카드 / 사진+글 카드)로 표현
- **소재**: 국내에서 활동하는 간첩 행위 + 간첩 의혹
- **v0.1 성격**: 정적 사이트, 열람 전용. 독자는 카드 피드를 보고 클릭해 상세를 확인할 뿐 상호작용(로그인·댓글·반응) 없음
- **v0.3 이후**: 제보자가 URL/사진/글을 보낼 수 있게 되어 콘텐츠 공급원이 사용자 본인 + 독자 제보로 확장

## 2. 타깃 사용자·핵심 가치 가설

### 페르소나 가설 (확정된 소재·톤·독자·운영자 정보 기반)

⚠️ 아래는 §0.5에서 **사용자가 확정한 소재·톤·독자 범주**만을 근거로 한 가설이다. 특정 개인·연령·직업 등 주어지지 않은 세부 인적 정보는 추가하지 않는다.

**P1 — 검색 유입 독자**
- 특정 간첩 행위·의혹 사건을 뉴스에서 접한 뒤, 관련 배경·경과를 검색으로 찾아 이 사이트에 도달
- 필요: 산발적으로 보도되는 정보를 한 곳에서 시간순·상태 라벨별로 정리해서 보고 싶음
- 핵심 가치: 원문 링크 신뢰성 + 사실/의혹 구분 표기(§6)로 "이 정보가 어디까지 확인된 것인지" 즉시 파악

**P2 — 관심사 커뮤니티 독자**
- 안보·시사 이슈에 지속적 관심을 갖고 재방문하는 독자(소재로부터 추론 — 확정 독자 범주는 "특정 관심사 커뮤니티"이며, 관심사의 구체 내용은 소재에서 자연스럽게 좁힌 것으로 별도로 확인된 사실은 아님)
- 필요: 태그로 관련 사건을 묶어서 추적, 신규 게시물 빠르게 확인
- 핵심 가치: 카드 피드의 훑어보기 경험(모바일 우선) + 공유(v0.5)로 관심사 커뮤니티 내 확산

### 핵심 가치 제안(USP) 가설
산발적으로 보도되는 간첩 행위·의혹 관련 뉴스를 **카드형으로 큐레이션**하고, **사실 확인 단계(§6① 상태 라벨)를 명시적으로 구분**해 보여주는 소식지. 원문 전재 없이 출처를 존중하며, 익명 운영자가 정보 전달에 집중한다.

### 남은 질문
- 예상 게시 빈도·이미지 볼륨 — 이미지 호스팅(public/R2) 판단, 피드 페이지당 게시물 수(N값), KPI 기준선 설정에 필요. (브랜드 비주얼 톤·기존 콘텐츠 유무는 §0.5에서 답변 완료 처리)

→ `planning/user-questions.md` 참조.

|---|---|---|

| 제목 | 카드·상세 타이틀 | URL 유형은 OG 제목 자동 추출값 기본, 수동 override 가능(§6④ 단정 문구 금지 규칙 준수) |
| 요약(description) | 1~2문장 요약 | 메타 description·AI 인용(§9)에 사용. URL 유형은 OG description 우선, 없으면 슈퍼바이저 작성(원문 문장 그대로 복제 금지). 사진/사진+글 유형은 캡션 또는 본문 첫 문장 중 슈퍼바이저가 선택해 작성 |

| 게시일 | 발행 시각 | 정렬 기준(피드는 최신순, 제안) |
| 🔴 상태 라벨 | `의혹` / `수사중` / `기소` / `유죄판결`(심급 필수) / `종결` | **필수 필드** — §6① 편집 정책 참조. 카드·상세 모두 표기. `유죄판결`은 심급(1심/2심/확정) 하위 필드 필수 |

#### 🔴 안정 ID 원칙 (v0.4~v0.6의 키)
1. `id`는 v0.4(좋아요/싫어요)·v0.5(공유수)·v0.6(댓글)가 외래키로 사용한다. **한 번 게시된 후 값 변경 금지**
2. `id`는 **frontmatter에 명시적으로 기록**하고, 파일명·제목 등 가변 값에서 파생하지 않는다
3. 삭제·비공개된 게시물의 `id`는 **재사용 금지**. 삭제 시 후속 데이터(반응·공유수·댓글) 보존/삭제 원칙은 v0.4 착수 시점 미결
4. URL 경로(`/post/[id]`)에 그대로 노출되므로 URL-safe 문자셋 요구. 한글 허용 여부는 프로그래머 제안

### 3.2 유형별 필드

**① URL(링크 카드)**
- 원문 URL (필수)
- OG 제목·OG 썸네일·OG 요약 (자동 추출, 수동 override 가능 — 추출 실패 대비). **자동 추출 제목·요약을 override하지 않은 경우 상세 페이지에 "원문 제목/요약(출처 인용)" 라벨을 표시**(§6③ P4 반영 — 출처 인용은 실명 표기 규칙의 예외)
- 사이트명(OG `site_name`, 추출 실패 시 슈퍼바이저 수동 입력)
- 🔴 `useSourceImage`(가칭, P4 반영·리뷰어 02 §7 항목6 요구, boolean, 기본값 `true`) — 원문 OG 썸네일을 카드 대표 이미지로 쓸지 여부. 슈퍼바이저가 얼굴 등 식별 정보가 노출된 썸네일을 발견하면 `false`로 전환해 플레이스홀더로 대체한다(§6③ 실무 적용 지점)

**② 사진**
- 이미지 1장 이상 (배열)
- **`alt` 텍스트 (필수)** — WCAG 2.2 AA 1.1.1 요건. 빌드 검증 스크립트에서 누락 시 오류 처리(§9 접근성 연동)
- 캡션(선택)

**③ 사진+글**
- 이미지 1장 이상 (배열), **`alt` 텍스트 (필수, ②와 동일)**
- 본문 텍스트(마크다운)

### 3.3 슈퍼바이저 작성 편의 요구사항
- frontmatter(YAML) + 본문(마크다운) 조합으로, 슈퍼바이저가 사진 파일만 `public/images/`(또는 R2)에 넣고 frontmatter에 필드를 채우는 수준으로 게시 가능해야 함
- URL 유형은 OG 자동 추출 스크립트/도구가 frontmatter 초안을 생성해주는 것을 프로그래머에게 제안(수동 전량 타이핑 방지)
- 빌드 시 필수 필드 누락(요약·대표 이미지·상태 라벨·alt 포함)·**근거 출처(`sources[]`) 최소 1건 누락**·`id` 중복을 검증하는 스크립트 필요

사용자 확정(2026-09-21): 무한스크롤 + "더 보기" 하이브리드 채택.

- N값(초기 로드 수)은 프로그래머·디자이너 협의, "게시 빈도·이미지 볼륨" 답변 후 조정(§2 남은 질문)

### 4.4 게시물 상세·view 화면 요구사항 (사용자 확정 반영)
- **카드(피드)**: 제목 + 대표 이미지(없으면 플레이스홀더) + 상태 라벨 배지. **본문·요약은 펼치지 않는다**
- **카드 클릭 → 상세 페이지 이동**
- **상세 페이지**: 상태 라벨 + 근거 출처(`sources[]`) 링크 + 상태 갱신 이력(있으면) + 출처 표기
  - URL 카드: OG 요약(또는 "원문 제목/요약" 라벨) + 원문 링크(§5.1 rel 정책 적용, 명확한 "외부 이동" CTA)
  - 사진/사진+글: 원본 화질 열람(과도한 압축 지양), 여러 장일 경우 갤러리/스와이프, 본문(사진+글)

## 5. URL 카드 인용·저작권 정책

### 5.1 URL 카드 (인용)
- OG 메타(제목·썸네일·요약)만 추출·표시 — **본문 전재 금지**
- 원문 출처 링크를 카드·상세 모두에 명확히 노출(클릭 시 새 탭)

#### 링크 `rel` 정책 (정책만 규정, 속성 문자열은 "제안")

| 링크 출처 | 정책 | 제안 속성(확정은 프로그래머) |
|---|---|---|
| 사용자(운영자) 큐레이션 원문 링크 (v0.1 URL 카드) | 출처 신호를 돌려준다 — 크롤 유도·연관성 차단하지 않음 | `target="_blank" rel="noopener"` |
| 제보(v0.3)·댓글(v0.6) 본문 내 사용자 삽입 링크 | 서비스와 무관함을 명시 | `rel="nofollow ugc noopener"` — ⚠️ 현 설계(§7 v0.3)에서 제보는 슈퍼바이저 검수를 거쳐 사용자 링크로 전환되므로, 이 행이 실제로 적용되는 대상은 **v0.6 댓글**뿐이다(검수 없이 노출되는 UGC) |
| 광고·제휴 링크(현재 없음) | 장래 대비 | `rel="sponsored"` |

> 근거: 큐레이션 소식지가 자신이 선택한 출처에 `nofollow`·`ugc`를 붙이는 것은 출처 존중 원칙과 어긋나며, `noreferrer`는 출처가 이 사이트발 유입을 인지하지 못하게 한다. 보안 목적(tabnabbing 방지)은 `noopener`만으로 충분하다.

#### OG 썸네일 처리 정책 (선택지·기본값 제시, 법률 판단은 확인 필요)

1. **저장 방식** — **기본값: 핫링크**(원 URL 그대로 참조). 재호스팅은 원 저작물의 복제에 해당해 저작권 리스크가 더 크고, 인용(미리보기) 목적에는 핫링크로 충분하다. ⚠️ **확인 필요**: 핫링크가 국내 저작권법상 "복제"에 해당하지 않는다는 실무 견해는 있으나 확정 판례는 확인하지 못했다.
2. **이 사이트 자체 OG 이미지로의 재사용 여부** — **기본값: 재사용하지 않음**. 소셜 공유 시 자체 로고/플레이스홀더를 사용하고, 원문 썸네일은 카드 내부 미리보기 용도로만 사용(§3.2① `useSourceImage` 스위치와 연동). 근거: 소재 특성상 원문 썸네일에 특정인 얼굴이 포함될 가능성이 있어 초상권 리스크가 겹친다(§6③ 연동).
3. **추출 실패·원본 삭제 시 플레이스홀더**: §4.4 view 화면 결정과 정합. 핫링크 깨짐 감지 시에도 자동 전환.
4. **원 사이트의 제거 요청 절차**: `/about`에 익명 운영과 양립 가능한 연락 채널(이메일 등) 마련 → 접수 후 사용자(운영자)가 확인해 이미지를 플레이스홀더로 교체 또는 게시물 비공개 → **1차 답변은 영업일 3일 이내, 실제 조치는 확인 즉시**(P5 처리기한 통일 — §6⑤와 동일 기준으로 정리)

- 요약이 OG description 없이 추출 불가할 경우 슈퍼바이저가 직접 1~2문장 요약 작성 가능해야 함(단 원문 문장 그대로 복제 금지)

### 5.2 사진 게시물
- 사용자 확정(2026-09-21): **슈퍼바이저는 게시 전 사진 저작권 관련 확인 절차를 별도로 두지 않는다.** 사용자가 게시를 요청하는 사진은 본인 촬영/소유 또는 게시 권한을 확보한 것으로 전제하며, 그 책임은 사용자에게 있다.
- 출처·촬영자 표기 필드를 두어 필요 시 기재
- 인물 식별 가능한 사진의 실명·얼굴 노출 기준은 §6③ 편집 정책을 따른다(단, ③은 운영자 작성 문구·자체 편집 이미지에 적용되며, 위 확인 절차 생략과는 별개다 — ③은 "게시 여부 확인"이 아니라 "게시 후 표기 방식"을 규정)

### 5.3 v0.3 제보 대비 사전 설계
- 제보자가 URL/사진/글을 제출할 때 다음 두 가지를 **필수 체크**로 받는다:
  1. **권리 보유 확인**: 제출 콘텐츠가 저작권 문제없는 것임을 확인
  2. **이용 허락**: 위 콘텐츠를 이 사이트에서 게시·리사이즈·크롭·공유 카드 생성 등에 사용하는 것을 허락
- 제보자 연락처(선택) 수집 시 **개인정보 수집·이용 동의**, 보관 기간 고지 필요 → v0.3 착수 전 개인정보처리방침 페이지 게시
- 제보 데이터에 "제보자 동의 여부" 필드를 처음부터 스키마에 넣어야 함

### ① 게시물 상태 라벨 (스키마 필수 필드, §3.1) — 5종 확정 (N2·N3 반영)

리뷰어 02 판정: 기소는 검사의 공소 제기일 뿐 유죄 판단이 아니다. 헌법 제27조④·형사소송법 제275조의2("피고인은 유죄의 판결이 확정될 때까지는 무죄로 추정된다" — 2026-09-21 법령 원문 직접 재확인, 현행 조문과 문구 동일함을 확인)가 무죄 추정을 명문화하므로, 기소 단계에 "확정"이라는 단어를 붙이지 않는다. 또한 무혐의·불기소·무죄 등으로 종결된 사건을 담을 라벨이 없으면 혐의가 해소된 사실이 표시되지 않거나 잘못된 라벨에 고정되는 위험이 있다(N2). 이에 따라 **5종 라벨**을 확정한다.

| 라벨 | 정의 | 카드 배지 |
|---|---|---|
| `의혹` | 언론 보도, 국회·시민단체 등의 주장·제보에 근거해 사실관계가 아직 공적으로 확인되지 않은 경우(단, ②의 허용 출처를 통해 인용된 경우에 한함) | — |
| `수사중` | 수사기관의 수사 개시·압수수색 등 공식 조치가 보도된 경우, 기소 전 | — |
| `기소` | 검사의 공소 제기가 보도·발표된 경우 ~ 판결 전(재판 진행 중 포함) | — |
| `유죄판결` | 법원의 유죄 판결이 보도되거나 판결문이 공개된 경우 | **심급 필수 병기**(1심/2심/확정) |
| `종결` | 무혐의·불기소·무죄·공소기각·공소취소 등으로 사건이 종결된 경우 | 사유는 상세 페이지에 텍스트로 표기 |

- **표기 규칙**: 카드에는 제목 옆/앞에 상태 배지 표시. 상세 페이지에는 상태 + 근거 출처(`sources[]`) 링크를 함께 명시
- 종결 게시물은 삭제하지 않고 라벨을 `종결`로 **갱신**한다(⑥ 참조, 안정 ID 원칙과 일치)

### ② 허용 출처 요건

- 언론사 보도, 수사기관(검찰·경찰·국가정보원 등) 공식 발표·보도자료, 공개된 법원 판결문 중 **최소 1개 이상**을 `sources[]`에 인용해야 게시 가능
- `의혹` 라벨의 근거로 "국회·시민단체 등의 주장"을 들 수 있으나, **그 주장이 위 언론사 보도를 통해 인용된 경우에 한해 인정**한다(단체·개인의 SNS·성명서를 직접 근거로 삼지 않는다, p2 반영)
- **허용 언론사 기본값** (P2, 법령 원문 직접 확인 — 「신문 등의 진흥에 관한 법률」 제2조·제9조): 제9조에 따라 시·도지사에 **등록**된 신문·인터넷신문(제2조 1호·2호 정의 충족), 「뉴스통신진흥에 관한 법률」상 뉴스통신사, 「방송법」상 방송사업자. 미등록 매체·1인 미디어·유튜브는 `의혹` 근거로도 불허.
- **등록 여부 조회**: 문화체육관광부 「정기간행물 등록관리시스템」(https://pds.mcst.go.kr/pds/, 2026-09-21 직접 접속 확인 — "제호 검색 서비스"로 지역·제호명·법인명별 등록 현황 조회 가능, 인터넷신문 13,951건·뉴스통신 40건 등 등록)에서 확인한다.

### ③ 실명·얼굴 표기 기준 (적용 범위 명확화 — P4 반영)

- **적용 대상**: 이 규칙은 **운영자(사용자)가 직접 작성·override하는 제목·요약·본문 문구**와 **자체 편집 이미지**(§3.2① `useSourceImage=false`로 전환해 대체하는 경우 등)에 적용된다.
- **자동 추출값의 예외**: URL 카드의 OG 자동 추출 제목·요약은 원문 그대로의 출처 인용이므로 이 규칙의 override 대상이 아니다 — 대신 상세 페이지에 "원문 제목/요약(출처 인용)" 라벨을 표시해 이것이 원문 그대로임을 명확히 한다(§3.2①).
- **기본 규칙**: `기소` 이전 단계(의혹/수사중)의 인물은 운영자 작성 문구에서 실명 대신 이니셜(예: "ㄱ씨") 사용, 얼굴은 노출하지 않음(자체 이미지 미사용, `useSourceImage=false`).
- **공인 예외**: 선출직·고위 공직자 등 언론이 이미 실명으로 보도한 인물은 언론 표기를 따른다(이니셜로 바꾸는 것이 식별을 막지 못하면서 정보 전달형 톤을 해치기 때문).
- `유죄판결`(심급 무관) 단계 인물은 실명 표기 가능. 미성년자 등은 예외적으로 비공개 유지.
- ⚠️ **확인 필요**: 원문 이미지의 얼굴을 모자이크 처리하는 것(가공)이 인용 범위 내 저작권법상 허용되는지는 법률 확인 필요 — 기본값은 가공하지 않고 `useSourceImage=false`로 대체하는 쪽을 택한다.

### ④ 운영자(사용자) 단정 문구 금지 실무 규칙
- 제목·요약을 수동으로 작성/override할 때 "~다", "~한 것으로 밝혀졌다" 등 단정 서술 대신 **"~로 보도됨"·"~라는 의혹이 제기됨"·"~로 기소됨(출처: OOO)"** 등 인용문 형태를 유지한다
- 법원이 확정하지 않은 죄명을 운영자가 스스로 붙이는 형용사적 단정 표현 금지

### ⑤ 정정·삭제 요청 접수 절차
- `/about`에 익명 운영과 양립 가능한 연락 채널(이메일 등) 마련
- 접수 → 사용자(운영자)가 원 출처 재확인 → 필요 시 상태 라벨 변경/게시물 수정/비공개 처리
- **처리기한 (P5 통일)**: **1차 답변은 영업일 3일 이내, 실제 조치는 확인 후 즉시** (법정 의무 아닌 서비스 정책, 사용자 확정 가능)

### ⑥ 상태 변경 시 갱신 규칙
- `의혹` → `수사중` → `기소` → `유죄판결` 또는 → **`종결`**(무혐의·불기소·무죄·공소기각 등) 진행 시 **원 게시물의 상태 라벨(가칭 `status`) 필드를 갱신**한다(안정 ID 원칙과 일치 — 새 게시물을 만들지 않는다)
- **종결로 갱신된 게시물은 삭제하지 않는다** — 기록 보존과 안정 ID 원칙에 따라 라벨만 갱신하고 게시물은 유지한다
- 상세 페이지에 갱신 이력(`statusHistory[]`, 예: "2026-XX-XX 상태 갱신: 의혹 → 기소")을 표시해 정보 왜곡을 방지한다

## 9. 6대 핵심 축별 적용 방안

### SEO
- 게시물별 `<title>`·meta description(§3.1 요약 필드)·OG 이미지(§5.1 처리 정책·`useSourceImage` 스위치 적용)
- `sitemap.xml` 자동 생성(빌드 시 `content/posts/` 스캔) → §8에서 GSC·네이버 서치어드바이저에 제출
- JSON-LD: 게시물 상세에 적합한 스키마.org 타입 마크업(구체 타입 선정은 프로그래머 제안 필요 — `NewsArticle`류는 언론사가 아닌 큐레이션 사이트에 적용 시 오해 소지가 있어 신중 검토)
- 태그 페이지도 canonical URL·메타 보유(카테고리 페이지는 v0.1에 없음)
- "더 보기" 링크는 실제 `<a href>`로 구현(§4.3)

### AI 검색 최적화 (GEO)
- 명확한 시맨틱 구조(제목-상태 라벨-요약-본문 위계) — LLM이 요약·인용하기 쉬운 구조
- `llms.txt` 도입 제안 — 프로그래머 판단
- 요약 필드(§3.1)를 AI 인용용으로 구조화

### 웹표준·시맨틱·접근성 (WCAG 2.2 AA)
- 사진·사진+글 게시물 `alt` 텍스트 **필수**(§3.2, 빌드 검증 스크립트로 게이트)
- 카드·상세 모두 키보드 탐색 가능, 포커스 인디케이터 명확
- 색 대비 4.5:1 이상 (디자이너 담당)
- 외부 링크는 시각적으로도 "외부 이동"임을 인지 가능하게(아이콘 등)

### 보안
- 외부 링크 `rel` 정책은 §5.1 표를 따른다(운영자 링크 vs UGC 링크 이원화)
- 마크다운 본문 렌더링 시 XSS 방지(sanitize, 원본 HTML 삽입 금지)
- **CSP 헤더 — `img-src` 정합 (P3 신설)**: OG 썸네일을 핫링크(§5.1①)하면 이미지 출처 도메인이 게시물마다 달라진다. `img-src`를 열거식 화이트리스트로 운영하면 새 출처마다 CSP 배포가 필요해 파일 커밋만으로 게시하는 파이프라인이 깨진다. **`img-src`는 `https:` 범위로 허용하거나(스크립트·프레임은 엄격 유지), 자체 이미지 프록시(재호스팅 아닌 캐시 없는 패스스루)를 경유하는 방식 중 하나를 프로그래머가 선택**해 TECH_STACK.md에 근거와 함께 기록한다. Next.js 이미지 최적화(`remotePatterns`) 정합도 함께 판단한다.

### UX/UI 친화성
- 모바일 우선: 카드 1열, 엄지 도달 영역 고려한 CTA 배치
- 진입 장벽 zero: 모든 버전에서 열람은 로그인 불필요(v0.6 댓글 "작성"만 인증이 필요할 수 있음 — 방식 미결)
- 로딩 속도: 정적 생성(SSG) 기반이므로 Lighthouse 90+ 목표

### 🔴 편집 정책 (사실·의혹 구분)
- 상세는 §6 참조. 요약: 모든 게시물은 상태 라벨(의혹/수사중/기소/유죄판결/종결) 5종 중 하나를 필수로 갖고, 허용 출처(§6②) 기반으로만 게시하며, 운영자 단정 문구를 금지하고, 정정·삭제 요청 절차를 상시 운영한다.

- **Google 공식 근거 (r4, 2026-09-21 직접 WebFetch 확인)**: Google Search Central "Mobile-first indexing best practices" 원문 — *"Google recommends Responsive Web Design because it's the easiest design pattern to implement and maintain."* (https://developers.google.com/search/docs/crawling-indexing/mobile/mobile-sites-mobile-first-indexing) — 모바일 퍼스트 인덱싱 환경에서도 반응형이 구현·유지보수 측면에서 권장됨을 확인
- 단, v0.3 이후 제보 폼·v0.6 댓글 UI 등 상호작용이 늘면 재검토 여지 있음
