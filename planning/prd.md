## 1. 서비스 정의

> 사용자 원문: "내가 슈퍼바이저에게 URL이나 사진, 사진&글을 주면 그게 게시되는, 카드 형태 뉴스 소식지 정도의 사이트. 모바일, 웹 모두 지원."

### 용어 정의

| 용어 | 정의 |
|---|---|
| **사용자** | 이 서비스의 소유자·운영자. 콘텐츠(URL·사진·글)를 결정하고 게시를 지시하는 주체. `/about`에서는 익명으로 남는다 |
| **슈퍼바이저** | 사용자의 지시를 받아 게시 파일(`content/posts/*.md`) 작성·커밋·배포를 수행하는 AI 세션(Opus 5). 독립된 운영 인격이 아니라 사용자의 게시 도구 |
| **독자** | 사이트를 열람하는 방문자. v0.1은 로그인·상호작용 없이 열람만 가능 |
| **제보자** | v0.3 이후 URL·사진·글을 제출하는 독자. 제보는 사용자(운영자)의 검수를 거쳐야 게시된다 |

> 정정: v0.1 초안 §1·§2에서 "게시 주체: 슈퍼바이저(운영자) 1인"으로 혼용했던 표현을 위 정의로 대체한다. 게시 결정 주체는 **사용자(운영자)**이며, 슈퍼바이저는 그 실행 도구다. `/about`에 "게시 파일은 AI 세션이 작성한다"는 사실을 고지할지는 §2 남은 질문 참조.

### 서비스 정의

- **형태**: 카드 피드 기반 소식지 사이트. 개별 게시물은 카드(링크 카드 / 사진 카드 / 사진+글 카드)로 표현
- **소재**: 국내에서 활동하는 간첩 행위 + 간첩 의혹
- **게시 주체**: 사용자(운영자)가 URL/사진/사진+글을 슈퍼바이저에게 전달 → 슈퍼바이저가 큐레이션·정리하여 게시
- **v0.1 성격**: 정적 사이트, 열람 전용. 독자는 카드 피드를 보고 클릭해 상세를 확인할 뿐 상호작용(로그인·댓글·반응) 없음
- **v0.3 이후**: 제보자가 URL/사진/글을 보낼 수 있게 되어 콘텐츠 공급원이 사용자 본인 + 독자 제보로 확장

## 2. 타깃 사용자·핵심 가치 가설

### 페르소나 가설 (확정된 소재·톤·독자·운영자 정보 기반)

⚠️ 아래는 §0.5에서 **사용자가 확정한 소재·톤·독자 범주**만을 근거로 한 가설이다. 특정 개인·연령·직업 등 주어지지 않은 세부 인적 정보는 추가하지 않는다.

**P1 — 검색 유입 독자**
- 특정 간첩 행위·의혹 사건을 뉴스에서 접한 뒤, 관련 배경·경과를 검색으로 찾아 이 사이트에 도달
- 필요: 산발적으로 보도되는 정보를 한 곳에서 시간순·상태(확정/수사중/의혹)별로 정리해서 보고 싶음
- 핵심 가치: 원문 링크 신뢰성 + 사실/의혹 구분 표기(§6)로 "이 정보가 어디까지 확인된 것인지" 즉시 파악

**P2 — 관심사 커뮤니티 독자**
- 안보·시사 이슈에 지속적 관심을 갖고 재방문하는 독자
- 필요: 카테고리·태그로 관련 사건을 묶어서 추적, 신규 게시물 빠르게 확인
- 핵심 가치: 카드 피드의 훑어보기 경험(모바일 우선) + 공유(v0.5)로 관심사 커뮤니티 내 확산

### 핵심 가치 제안(USP) 가설
산발적으로 보도되는 간첩 행위·의혹 관련 뉴스를 **카드형으로 큐레이션**하고, **사실 확인 단계(확정/수사중/의혹)를 명시적으로 구분**해 보여주는 소식지. 원문 전재 없이 출처를 존중하며, 익명 운영자가 정보 전달에 집중한다.

### 남은 질문 (페르소나·기획 세부에 영향)
1. 예상 게시 빈도·이미지 볼륨 — 이미지 호스팅(public/R2) 판단, 피드 페이지당 게시물 수(N값), KPI 기준선 설정에 필요
2. 기존 보유 콘텐츠 유무 — v0.1 초기 게시물 물량 파악에 필요
3. 브랜드 비주얼 톤(로고·색감 등 디자인 무드) — 콘텐츠 톤(정보 전달형)과 별개로 디자이너 착수 전 필요

→ `planning/user-questions.md` 참조.

## 3. 게시물 모델 (콘텐츠 스키마 요구사항)

> 🔴 구체 스키마(필드명·타입) 확정은 프로그래머 몫. 여기서는 요구사항만 규정한다.

### 3.1 공통 필드 (3종 유형 모두)

| 필드(가칭) | 설명 | 비고 |
|---|---|---|
| `id`(슬러그) | 게시물 고유 식별자 | 🔴 **안정 ID 원칙** — 아래 4개 규칙 |
| 제목 | 카드·상세 타이틀 | URL 유형은 OG 제목 자동 추출값 기본, 수동 override 가능(§6④ 단정 문구 금지 규칙 준수) |
| 요약(description) | 1~2문장 요약 | 메타 description·AI 인용(§9)에 사용. URL 유형은 OG description 우선, 없으면 슈퍼바이저 작성(원문 문장 그대로 복제 금지). 사진/사진+글 유형은 캡션 또는 본문 첫 문장 중 슈퍼바이저가 선택해 작성 |
| 대표 이미지 | 카드 피드에 노출할 이미지 | view 화면 결정과 연동. URL 유형은 OG 썸네일(§5.1 처리 정책 적용), 사진·사진+글 유형은 첫 번째 이미지. 이미지가 없거나 처리 정책상 사용 불가하면 플레이스홀더 |
| 게시일 | 발행 시각 | 정렬 기준(피드는 최신순, 제안) |
| 상태 라벨 | `확정` / `수사중` / `의혹` | 🔴 **필수 필드** — §6① 편집 정책 참조. 카드·상세 모두 표기 |
| 카테고리 | 단일 카테고리 | 체계는 §4.2, 사용자 확정 대기 |
| 태그 | 다중 태그 | 선택 입력 |
| 출처 유형 | `url` / `photo` / `photo_text` | 카드 렌더링 분기 기준 |
| 출처 표기 | URL 유형: 원문 출처명·링크 / 사진 유형: 촬영자·제공처 | §5.2 저작권 정책 연동 |

#### 🔴 안정 ID 원칙 (v0.4~v0.6의 키)
1. `id`는 v0.4(좋아요/싫어요)·v0.5(공유수)·v0.6(댓글)가 외래키로 사용한다. **한 번 게시된 후 값 변경 금지**
2. `id`는 **frontmatter에 명시적으로 기록**하고, 파일명·제목 등 가변 값에서 파생하지 않는다(파일명 변경 = id 변경 사고 방지)
3. 삭제·비공개된 게시물의 `id`는 **재사용 금지**(과거 반응·댓글 데이터가 새 게시물에 잘못 연결되는 사고 방지). 삭제 시 후속 데이터(반응·공유수·댓글) 보존/삭제 원칙은 v0.4 착수 시점 미결 — 지금은 원칙만 명시
4. URL 경로(`/post/[id]`)에 그대로 노출되므로 URL-safe 문자셋 요구. 한글 허용 여부는 프로그래머 제안

### 3.2 유형별 필드

**① URL(링크 카드)**
- 원문 URL (필수)
- OG 제목·OG 썸네일·OG 요약 (자동 추출, 수동 override 가능 — 추출 실패 대비)
- 사이트명(OG `site_name`, 추출 실패 시 슈퍼바이저 수동 입력)

**② 사진**
- 이미지 1장 이상 (배열)
- **`alt` 텍스트 (필수)** — WCAG 2.2 AA 1.1.1 요건. 빌드 검증 스크립트에서 누락 시 오류 처리(§9 접근성 연동)
- 캡션(선택)

**③ 사진+글**
- 이미지 1장 이상 (배열), **`alt` 텍스트 (필수, ②와 동일)**
- 본문 텍스트(마크다운)

### 3.3 슈퍼바이저 작성 편의 요구사항
- frontmatter(YAML) + 본문(마크다운) 조합으로, 슈퍼바이저가 사진 파일만 `public/images/`(또는 R2)에 넣고 frontmatter에 필드를 채우는 수준으로 게시 가능해야 함
- URL 유형은 OG 자동 추출 스크립트/도구가 frontmatter 초안을 생성해주는 것을 프로그래머에게 제안(수동 전량 타이핑 방지)
- 빌드 시 필수 필드 누락(요약·대표 이미지·상태 라벨·alt 포함)·`id` 중복을 검증하는 스크립트 필요

## 4. 정보구조(IA)·핵심 화면

### 4.1 사이트맵 (v0.1)

```
/                     — 홈 (카드 피드, 최신순 정렬 제안)
/category/[slug]      — 카테고리별 피드
/tag/[slug]           — 태그별 피드
/post/[id]            — 게시물 상세
/about                — 소개 + 출처·저작권 정책 + 정정·삭제 요청 접수(§6⑤)
```
> v0.3부터 개인정보처리방침 페이지 추가 필요(§5.3·§7 v0.3 DoD).

### 4.2 카테고리 체계 — 재제안 (확정 필요)
소재(간첩 행위·의혹)가 확정되었으므로 주제 기반 카테고리를 제안한다. **카테고리(주제 분류)와 상태 라벨(§3.1, 확정/수사중/의혹)은 서로 다른 축**이며, 게시물은 카테고리 1개 + 상태 라벨 1개를 동시에 가진다(카테고리를 사실확인 단계로 대체하지 않는다 — 두 축을 혼동하면 카드에 정보가 중복 표시된다).

**제안 (5개, 5±2 원칙)**
1. 산업·기술 기밀유출
2. 정치·공직 연루 의혹
3. 군사·안보 사건
4. 사이버·해킹 공작
5. 해외 사례·국제 동향

- 근거: 간첩 행위·의혹이라는 단일 소재 안에서도 유형이 뚜렷이 나뉘어 독자가 관심사(P2 페르소나)를 좁혀 탐색할 수 있음
- **사용자 확정 필요**: 카테고리명·개수·5번 "해외 사례" 포함 여부(국내 소재 원칙과 범위가 겹칠 수 있어 확인 필요)

### 4.3 피드 방식 — 무한스크롤 + "더 보기" 하이브리드 (기본 채택)
- SEO 근거: 크롤러는 버튼 클릭·JS 트리거를 따라가지 않으므로, "더 보기" 컨트롤은 **`<a href="?page=n">` 형태의 실제 링크**여야 한다(버튼+JS만으로 구현 시 하위 카드가 크롤링되지 않음). 초기 N장 서버 렌더 + 이후 청크는 `?page=n` URL로 접근 가능해야 함
- 무한스크롤 자체의 UX 이점(연속 열람)은 유지하되, "공유·재방문 지점 특정" 논거는 근거 부족으로 제외한다 — 이 서비스의 공유 단위는 상세 페이지(`/post/[id]`)이며 피드 페이지 자체를 공유하는 시나리오는 확인되지 않았다
- N값(초기 로드 수)은 프로그래머·디자이너 협의, §2 "게시 빈도·이미지 볼륨" 답변 후 조정
- **처리 방식**: 이 항목은 UX 세부 영역으로 기본 채택하고 진행한다. 사용자가 이의를 제기하면 변경한다(§0.5 미결 표 표기와 일치)

### 4.4 게시물 상세·view 화면 요구사항 (사용자 확정 반영)
- **카드(피드)**: 제목 + 대표 이미지(없으면 플레이스홀더로 카드 형태 유지) + 상태 라벨 배지. **본문·요약은 펼치지 않는다**
- **카드 클릭 → 상세 페이지 이동**
- **상세 페이지**:
  - URL 카드: 상태 라벨 + OG 요약 + 원문 링크(§5.1 rel 정책 적용, 명확한 "외부 이동" CTA) + 출처 표기
  - 사진/사진+글: 상태 라벨 + 원본 화질 열람(과도한 압축 지양), 여러 장일 경우 갤러리/스와이프, 본문(사진+글)

## 5. URL 카드 인용·저작권 정책

### 5.1 URL 카드 (인용)
- OG 메타(제목·썸네일·요약)만 추출·표시 — **본문 전재 금지**
- 원문 출처 링크를 카드·상세 모두에 명확히 노출(클릭 시 새 탭)

#### 링크 `rel` 정책 (D1 반영 — 정책만 규정, 속성 문자열은 "제안")

| 링크 출처 | 정책 | 제안 속성(확정은 프로그래머) |
|---|---|---|
| 사용자(운영자) 큐레이션 원문 링크 (v0.1 URL 카드) | 출처 신호를 돌려준다 — 크롤 유도·연관성 차단하지 않음 | `target="_blank" rel="noopener"` |
| 제보(v0.3)·댓글(v0.6) 본문 내 사용자 삽입 링크(검수 없이 노출되는 UGC) | 서비스와 무관함을 명시 | `rel="nofollow ugc noopener"` |
| 광고·제휴 링크(현재 없음) | 장래 대비 | `rel="sponsored"` |

> 근거: 큐레이션 소식지가 자신이 선택한 출처에 `nofollow`·`ugc`를 붙이는 것은 출처 존중 원칙(§9 보안·저작권 축)과 어긋나며, `noreferrer`는 출처가 이 사이트발 유입을 인지하지 못하게 해 관계 형성을 스스로 차단한다. 보안 목적(tabnabbing 방지)은 `noopener`만으로 충분하다. UGC(제보·댓글)는 검수 여부에 따라 구분한다 — 게시 시점에 사용자가 검수해 게시하는 제보는 "사용자 큐레이션 링크"로 전환되므로 위 표의 상단 정책이 적용되고, 검수 없이 그대로 노출되는 링크(예: 댓글 내 링크)만 UGC 정책을 적용한다.

#### OG 썸네일 처리 정책 (D3 신설 — 선택지·기본값 제시, 법률 판단은 확인 필요)

1. **저장 방식** — 옵션 A: 핫링크(원 URL 그대로 참조) / 옵션 B: 재호스팅(다운로드 후 자체 저장)
   - **기본값 제안: 핫링크**. 재호스팅은 원 저작물의 복제에 해당해 저작권 리스크가 더 크고, 인용(미리보기) 목적에는 핫링크로 충분하다. 다만 핫링크는 원 사이트의 이미지 삭제·URL 변경 시 깨진다.
   - ⚠️ **확인 필요**: 핫링크가 국내 저작권법상 "복제"에 해당하지 않는다는 실무 견해는 있으나 확정 판례를 확인하지 못했다.
2. **이 사이트 자체 OG 이미지로의 재사용 여부**
   - **기본값 제안: 재사용하지 않음**. 게시물 소셜 공유 시(카카오톡 등) 이 사이트 명의 OG 이미지는 자체 로고/플레이스홀더를 사용하고, 원문 썸네일은 카드 내부 미리보기 용도로만 사용한다.
   - 근거: 소재 특성상 원문 썸네일에 특정인 얼굴이 포함될 가능성이 있다. 제3자 이미지를 자사 명의 소셜 공유 미리보기로 내보내는 것은 인용 범위를 넘어설 소지가 있고 초상권 리스크가 겹친다(§6③ 연동).
   - ⚠️ **확인 필요**: 위 리스크 평가는 리스크 식별이며 법률 자문은 아니다.
3. **추출 실패·원본 삭제 시 플레이스홀더**: §4.4 view 화면 결정(카드 = 제목+이미지, 없으면 플레이스홀더)과 정합. 핫링크 깨짐 감지 시에도 자동으로 플레이스홀더 전환(프로그래머 구현)
4. **원 사이트의 제거 요청 절차**: `/about`에 익명 운영과 양립 가능한 연락 채널(이메일 등) 마련 → 접수 후 사용자(운영자)가 확인해 해당 이미지를 플레이스홀더로 즉시 교체 또는 게시물 비공개 → 처리기한 제안: 영업일 3일 이내 1차 조치(법정 기한 아닌 서비스 정책, 사용자 확정 가능)

- 요약이 OG description 없이 추출 불가할 경우 슈퍼바이저가 직접 1~2문장 요약 작성 가능해야 함(단 원문 문장 그대로 복제 금지)

### 5.2 사진 게시물
- **전제**: 사용자가 게시를 요청하는 사진은 본인 촬영/소유 또는 게시 권한을 확보한 것으로 간주(확인 절차 세부는 §0.5 미결 표·`user-questions.md` 참조)
- 출처·촬영자 표기 필드를 두어 필요 시 기재
- 인물 식별 가능한 사진의 실명·얼굴 노출 기준은 §6③ 편집 정책을 따른다

### 5.3 v0.3 제보 대비 사전 설계
- 제보자가 URL/사진/글을 제출할 때 다음 두 가지를 **필수 체크**로 받는다(모달리티 통일):
  1. **권리 보유 확인**: 제출 콘텐츠가 저작권 문제없는 것임을 확인
  2. **이용 허락**: 위 콘텐츠를 이 사이트에서 게시·리사이즈·크롭·공유 카드 생성 등에 사용하는 것을 허락
- 제보자 연락처(선택) 수집 시 **개인정보 수집·이용 동의**, 보관 기간 고지 필요 → v0.3 착수 전 개인정보처리방침 페이지 게시(§7 v0.3 DoD에 반영)
- 제보 데이터에 "제보자 동의 여부" 필드를 처음부터 스키마에 넣어야 함(v0.3 착수 시 소급 추가는 리스크)

## 6. 🔴 편집 정책 — 사실·의혹 구분

> CLAUDE.md 핵심 축 6번. 소재가 특정 개인·단체를 향한 간첩 행위·의혹 서술이므로 명예훼손(사실적시 포함)·허위사실·초상권 리스크가 실재한다. **리뷰어는 이 절을 v0.2 게이트의 최우선 항목으로 본다.**

### ① 게시물 상태 라벨 (스키마 필수 필드, §3.1)
- `확정`: 법원 판결(심급 명시) 또는 수사기관의 기소 사실이 보도·발표된 경우
- `수사중`: 수사기관의 수사 개시·압수수색 등 공식 조치가 보도된 경우, 기소 전
- `의혹`: 언론 보도, 국회·시민단체 등의 주장·제보에 근거해 사실관계가 아직 공적으로 확인되지 않은 경우
- **표기 규칙**: 카드에는 제목 옆/앞에 상태 배지 표시. 상세 페이지에는 상태 + 근거 출처 링크를 함께 명시

### ② 허용 출처 요건
- 언론사 보도, 수사기관(검찰·경찰·국가정보원 등) 공식 발표·보도자료, 공개된 법원 판결문 중 **최소 1개 이상**을 인용해야 게시 가능
- 미확인 SNS 게시물·익명 제보만으로는 `의혹` 상태라도 게시 불가
- ⚠️ **확인 필요**: "정식 언론사" 판단 기준(등록 여부 등) 세부는 사용자 확정 또는 운영 재량

### ③ 실명·얼굴 표기 기준 (OG 썸네일 포함, §5.1 연동)
- **기본값 제안**: `확정` 단계에 도달하지 않은 인물은 실명 대신 이니셜(예: "ㄱ씨") 사용, 얼굴은 노출하지 않음(모자이크 또는 §5.1 정책에 따라 원문 썸네일 자체를 사용하지 않음)
- `확정` 단계라도 미성년자 등은 예외적으로 비공개 유지
- ⚠️ **확인 필요**: 원문 이미지에 이미 노출된 얼굴을 모자이크 처리하려면 재호스팅(가공)이 필요해질 수 있어 §5.1의 "재호스팅 지양" 원칙과 상충 여지 — 이 경우 인용 범위 내 가공(모자이크)의 저작권법상 허용 여부는 법률 확인 필요. 기본값: 얼굴이 식별되는 원문 썸네일은 사용하지 않고 플레이스홀더로 대체

### ④ 운영자(사용자) 단정 문구 금지 실무 규칙
- 제목·요약을 수동으로 작성/override할 때 "~다", "~한 것으로 밝혀졌다" 등 단정 서술 대신 **"~로 보도됨"·"~라는 의혹이 제기됨"·"~로 기소됨(출처: OOO)"** 등 인용문 형태를 유지한다
- 법원이 확정하지 않은 죄명을 운영자가 스스로 붙이는 형용사적 단정 표현 금지

### ⑤ 정정·삭제 요청 접수 절차
- `/about`에 익명 운영과 양립 가능한 연락 채널(이메일 등) 마련
- 접수 → 사용자(운영자)가 원 출처 재확인 → 필요 시 상태 라벨 변경/게시물 수정/비공개 처리
- 처리기한 제안: 영업일 5일 이내 1차 답변(법정 의무 아닌 서비스 정책, 사용자 확정 가능)

### ⑥ 상태 변경 시 갱신 규칙
- 의혹 → 수사중 → 확정(또는 무혐의·무죄로 종결) 등 진행 시 **원 게시물의 `status` 필드를 갱신**한다(안정 ID 원칙과 일치 — 새 게시물을 만들지 않는다)
- 상세 페이지에 갱신 이력(예: "2026-XX-XX 상태 갱신: 의혹 → 기소")을 표시해 정보 왜곡을 방지한다

## 7. 후속 사이클 사전 설계 (골조만 — v0.1 스키마 영향만 명시)

### v0.3 — 제보받기
- **입력 항목**: URL / 사진 / 사진+글 (v0.1 게시물 유형과 동일 3종) + 제보자 연락처(선택) + 권리 보유 확인 + 이용 허락(§5.3, 필수 체크로 통일)

- **슈퍼바이저 검수 흐름**: 제보 → 별도 저장소(Supabase 테이블, **이 프로젝트 전용 신규 계정** — 다른 프로젝트 키 재사용 금지) → 사용자 알림(Resend, 동일하게 전용 신규 계정) → 검수 후 승인 시 사용자 지시에 따라 슈퍼바이저가 `content/posts/`로 파일 작성(제보 원문을 그대로 게시하지 않고 정제, §6④ 단정 문구 금지 규칙 적용)
- **v0.1 스키마 요구사항**: 게시물에 "제보 출처 여부"를 표기할 선택 필드(`submittedBy` 또는 유사) 여지를 프로그래머가 미리 고려
- **DoD 추가**: 개인정보처리방침 페이지 게시(§5.3)

### v0.4 — 좋아요/싫어요
- **방식 후보**: 익명 1인 1표 — 브라우저 로컬 식별자(localStorage 우선) + 서버 집계(Supabase, 전용 신규 계정). 로그인 없는 v0.1 전제와 일관
  - ⚠️ fingerprint 방식은 개인정보보호법상 식별자로 고지 이슈가 있음 — localStorage를 우선하고, fingerprint를 병행할 경우 고지 필요
- **v0.1 스키마 요구사항**: `id`(안정 슬러그)가 반응 카운트의 외래키가 됨 — §3.1 안정 ID 원칙 재확인

### v0.5 — 공유 + 공유수 표시
- **공유 수단 후보**: 링크 복사, 카카오톡 공유하기, (선택) X/트위터
- **공유수 집계 정의**: "공유 버튼 클릭 수" 기준(실제 도달 여부까지 추적하지 않음, v0.1 단순화 원칙과 일치)
- **v0.1 스키마 요구사항**: `id` 기준 카운트 저장(v0.4와 동일 패턴)

### v0.6 — 댓글
- **미결**: 익명 댓글 허용 vs 최소 인증(닉네임+비밀번호 또는 소셜 로그인) — 스팸·악성 댓글 리스크와 "로그인 없음" 원칙이 충돌하므로 착수 전 사용자 확정 필요

## 9. 6대 핵심 축별 적용 방안

### SEO
- 게시물별 `<title>`·meta description(§3.1 요약 필드)·OG 이미지(§5.1 처리 정책 적용)
- `sitemap.xml` 자동 생성(빌드 시 `content/posts/` 스캔) → §8에서 GSC·네이버 서치어드바이저에 제출
- JSON-LD: 게시물 상세에 적합한 스키마.org 타입 마크업(구체 타입 선정은 프로그래머 제안 필요 — 소재 특성상 `NewsArticle`류는 언론사가 아닌 큐레이션 사이트에 적용 시 오해 소지가 있어 신중 검토)
- 카테고리·태그 페이지도 canonical URL·메타 보유(중복 콘텐츠 방지)
- "더 보기" 링크는 실제 `<a href>`로 구현(§4.3)

### AI 검색 최적화 (GEO)
- 명확한 시맨틱 구조(제목-상태 라벨-요약-본문 위계) — LLM이 요약·인용하기 쉬운 구조
- `llms.txt` 도입 제안(사이트 목적·주요 섹션 안내) — 프로그래머 판단
- 요약 필드(§3.1)를 AI 인용용으로 구조화(메타 description과 공유 가능)

### 웹표준·시맨틱·접근성 (WCAG 2.2 AA)
- 사진·사진+글 게시물 `alt` 텍스트 **필수**(§3.2, 빌드 검증 스크립트로 게이트)
- 카드·상세 모두 키보드 탐색 가능, 포커스 인디케이터 명확
- 색 대비 4.5:1 이상 (디자이너 담당)
- 외부 링크는 시각적으로도 "외부 이동"임을 인지 가능하게(아이콘 등)

### 보안
- 외부 링크 `rel` 정책은 §5.1 표를 따른다(운영자 링크 vs UGC 링크 이원화)
- 마크다운 본문 렌더링 시 XSS 방지(sanitize, 원본 HTML 삽입 금지)
- CSP 헤더(Vercel 설정) — 이미지·폰트 출처 화이트리스트

### UX/UI 친화성
- 모바일 우선: 카드 1열, 엄지 도달 영역 고려한 CTA 배치
- 진입 장벽 zero: 모든 버전에서 열람은 로그인 불필요(v0.6 댓글 "작성"만 인증이 필요할 수 있음 — 방식 미결)
- 로딩 속도: 정적 생성(SSG) 기반이므로 Lighthouse 90+ 목표

### 🔴 편집 정책 (사실·의혹 구분)
- 상세는 §6 참조. 요약: 모든 게시물은 상태 라벨(확정/수사중/의혹)을 필수로 갖고, 허용 출처 기반으로만 게시하며, 운영자 단정 문구를 금지하고, 정정·삭제 요청 절차를 상시 운영한다.
