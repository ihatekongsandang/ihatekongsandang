## 1. Q1 — 게시물 주소(id) 이전과 리다이렉트

### 1.1 새 id

| 구분 | 값 |
|---|---|
| 옛 id | `2026-08-06-owloffreedom-<이름 로마자>-sentencing` (파일명·frontmatter `id`·영어본·이미지 폴더 이름에 쓰였다) |
| **새 id** | **`2026-08-06-owloffreedom-707-commander-sentencing`** |

**고른 근거**
- 형식 규칙(`ID_PATTERN = ^[a-z0-9]+(?:-[a-z0-9]+)*$`)을 지킨다. 길이 48자로 현행 최장 id(58자)보다 짧다.
- 날짜(발행일 유지)·계정 핸들·사건 낱말 순서가 다른 게시물과 같다.
- 사건 낱말 `707-commander`는 제목에 이미 있는 직함("전 707특임단장")과 같은 정보라 **새로 드러나는 것이 없다**. 이름의 로마자·초성은 id에 쓰지 않는다.
- 중복·폐기 충돌 없음: `content/posts/`·`content/retired-ids.txt`에 같은 id가 없다(직접 확인).

**일반 규칙(새 id를 지을 때, `content/README.md` id 행·guide §4에 한 줄로)**: 비공인 인물의 이름(로마자·음차)은 id·파일명·이미지 폴더에 쓰지 않는다. 직함·기관·사건 낱말로 짓는다. 공인이어도 확정 판결 전 범죄 사안이면 같은 방식을 권한다. id는 §6③이 정한 본문 표기 규칙보다 한 번 더 노출되는 곳(주소창·사이트맵·공유 링크)이라는 점을 업로더 점검표에 넣는다.

### 1.2 방식 비교와 결정

| 방식 | 정적 배포(SSG)에서 | 결정 |
|---|---|---|
| **`next.config.ts` `redirects()`** | ✅ 빌드 때 라우팅 규칙으로 컴파일되어 Vercel 라우팅 단계에서 처리된다(서버 함수 호출 없음). `next start`(로컬)에서도 같은 규칙이 돈다. Next 문서의 처리 순서는 headers → **redirects** → middleware → 파일시스템이라, 옛 주소는 `dynamicParams = false`의 404에 닿기 전에 넘어간다 | **채택** |
| `vercel.json` `redirects` | Vercel에서만 동작하고 `next start`로는 시험할 수 없다. JSON이라 `moved-ids.txt`에서 만들어 넣을 수도 없어 두 곳을 손으로 맞춰야 한다 | 기각 |
| `middleware.ts` | 동작은 하지만 모든 요청이 거치는 코드에 옮긴 id 목록을 넣게 된다. 지금 matcher는 `/`·`/tag/:slug`·`/en` 3개뿐이다 | 기각 |
| 페이지에서 `permanentRedirect()` + 옛 id를 정적 경로에 유지 | 옛 id가 `generateStaticParams`·사이트맵 후보에 되살아나고, 정적 생성 페이지에서는 HTTP 3xx가 아닌 HTML 이동이 될 수 있다(미시험 — 채택하지 않으므로 시험하지 않았다) | 기각 |
| 메타 refresh·JS 이동 | 검색엔진이 영구 이전으로 읽지 못한다 | 기각 |

> 동작 근거는 Next 문서의 처리 순서와 프로젝트의 선례(`next.config.ts`가 이미 `fs`로 `vercel.json`을 읽는다)다. **실제 동작은 프로그래머 16이 로컬 프로덕션 빌드에서, 배포 후 슈퍼바이저가 `curl -I`로 실측**한다(§1.7). 이 문서는 빌드·배포를 하지 않았다.

### 1.3 파일 사양

**`content/moved-ids.txt`** (새 파일, 형식은 `retired-ids.txt`와 같다)
```
# 옮긴 게시물 id 목록 — 옛 주소 → 새 주소 (308)
# 형식: 한 줄에 `옛id 새id` (공백으로 구분). `#` 뒤는 주석.
# 여기 적는 옛 id는 반드시 retired-ids.txt에도 있어야 한다(재사용 금지).
# 예: example-old-id example-new-id
```
- 🔴 **예시 줄도 반드시 `#` 주석으로 둔다.** 주석이 아닌 예시 줄이 실제 파일에 있으면 검증 d·f에 걸려 빌드가 실패하거나, 검증을 우회하면 없는 주소로 가는 이동 규칙이 실제로 생긴다(리뷰 34 P2-1). **C11이 처음 배포하는 `moved-ids.txt`는 주석만 있는 상태**이고, 실제 줄은 업로더 02가 넣는다.
- 실제 줄은 업로더가 넣는다: `<옛 id> 2026-08-06-owloffreedom-707-commander-sentencing`.
- `retired-ids.txt`에는 옛 id를 한 줄 추가한다(기존 방식 그대로: `# 이름 노출로 id 변경(2026-11-09)` 같은 주석).
- 두 파일이 각자의 역할을 맡는다: **`retired-ids.txt` = 이 id를 다른 게시물에 다시 쓰지 못하게 막는다. `moved-ids.txt` = 이 옛 주소를 어디로 보낼지 정한다.**

**공유 함수** `src/lib/content/moved-ids.ts` — `readMovedIds(): Map<string, string>`. 검증 스크립트(`scripts/validate-content.ts`)·로더(`load.ts`)·`next.config.ts`가 **같은 함수를 쓴다**(`retired-ids.ts`가 이미 이 이유로 그렇게 되어 있다). `next.config.ts`가 `src/` 파일을 불러올 수 없으면(제약은 프로그래머가 확인) 설정 안에 30줄 안팎의 읽기 코드를 두고, **단위 테스트가 두 구현의 출력이 같은지** 비교한다.

### 1.5 검증 규칙(빌드 중단 8가지, `validate-content`·로더 공통)
`moved-ids.txt`의 각 줄(`옛id 새id`)에 대해:

| # | 규칙 | 막는 사고 |
|---|---|---|
| a | 줄 형식이 `옛id 새id`(두 토큰) | 오타 줄이 조용히 무시됨 |
| b | 두 id 모두 `ID_PATTERN` | 잘못된 주소 규칙 |
| c | 옛 id ≠ 새 id | 무한 이동 |
| d | **옛 id가 `retired-ids.txt`에 있다** | 옮긴 옛 id가 다른 글에 재사용됨(반응·댓글 키 오염) |
| e | **옛 id를 쓰는 게시물이 `content/posts/`에 없다** | 살아 있는 글이 리다이렉트에 가려짐 |
| f | **새 id를 쓰는 게시물이 `content/posts/`에 있고, `retired-ids.txt`에 없다** | 없는 곳으로 보냄(404 이동) |
| g | 옛 id가 두 번 나오지 않는다 / **새 id가 다른 줄의 옛 id가 아니다**(연쇄·순환 금지, 손으로 최종 id에 맞춘다) | 이동 사슬·순환 |
| h | 본문(ko·en)의 `/post/…`·`/en/post/…` 링크가 옮긴 **옛 id를 가리키지 않는다** | 리다이렉트에 의존하는 내부 링크 |

규칙은 a~h 8가지다. 검증 실패 메시지는 `retiredIdMessage`처럼 한 함수로 만든다.

### 1.6 같은 일이 또 생길 때의 절차(일반 규칙, 업로더 지침·`content/README.md`에 옮긴다)
1. 슈퍼바이저가 사유와 새 id를 정한다(위 §1.1 규칙). 사용자 결정이 필요한 것은 "id를 바꿔도 되는가"뿐이다.
2. 파일 이동: `content/posts/<옛>.md`→`<새>.md`, 영어본, `public/images/<옛>/`→`<새>/`(이미지가 있으면). frontmatter `id`(ko·en 둘 다)와 `image.src`를 고친다.
3. `content/` 전체에서 옛 id를 grep해 본문 링크를 새 id로 고친다(0건이어야 완료).
4. `retired-ids.txt`에 옛 id 한 줄, `moved-ids.txt`에 `옛 새` 한 줄 추가.

조건: 인스타그램 4건 + 스레드 1건. 요청 사이 2초. UA `Mozilla/5.0`(guide §3). 받은 파일은 저장소 밖 스크래치 폴더에만 두고 데이터로만 다뤘다(서명 주소 원문은 저장소에 옮기지 않았다). 기록: `docs/tools/planner-16/hotlink-test-log.md`, 도구: `docs/tools/planner-16/hotlink-probe.sh`.

**해석(사실에서 나온 판단)**
- 이미지 주소가 게시물 주소(`/p/코드`)로부터 안정적으로 만들어지지 않고, **임베드 페이지를 새로 읽어야 얻는다.** 얻은 주소는 며칠 안에 만료되는 서명 주소다. 이 사이트는 정적 사이트라 주소를 `content/`에 적어 두면 만료 시각 이후 깨질 가능성이 크다. **만료 뒤 실제로 깨지는지는 미실측**이다(만료 후 동작은 위 표대로 시험하지 못했고, 시각을 지난 뒤 재시험한다). 서명을 바꾼 주소가 403이었다는 리뷰 34의 재시험은 "서명이 맞아야 열린다"는 근거이지 만료 후 동작의 실측이 아니다.
- 스레드는 이 표본에서 영상만 받을 수 있고 `<img>`에 쓸 이미지 주소가 없다.
- 그래서 **① 원문 이미지 핫링크는 현행 구조(`content/`의 고정 주소 + 정적 빌드 + 주 1회 점검)로는 쓸 수 없다.** 쓰려면 방문자의 브라우저가 열 때마다 서버를 거쳐 새 주소를 받아 오는 구조(서버 코드·프록시 또는 외부 임베드 스크립트)가 필요한데, 그것은 ① 정책 §1.1이 금지한 프록시·서버 캐시이거나, 카드 구조를 바꾸는 별도 사양이다. **그 구조는 이번에 시험하지 않았고(확인 필요), 권하지 않는다.**
- 접속 수: 인스타그램 임베드 페이지 4 + 스레드 1 + 이미지 8(Referer 2종 × 4) + 스레드 영상 1(1KB 범위 요청) + 재요청 4 + 새 임베드 1 = 19회, 모두 2초 이상 간격. 표본은 5건.

**재시험(필요 시, 슈퍼바이저)**: 만료 후 동작을 보려면 `bash docs/tools/planner-16/hotlink-probe.sh <저장소 밖 폴더> <게시물코드>`로 주소를 받고, **2026-11-14 이후에 같은 주소**를 다시 요청해 응답 코드를 비교한다(작업 폴더에 `url-*.txt`가 남는다). 요청 수는 표본 5건 이하로 지킨다.

### 3.5 사용자 결정 — 확정 (Q3 = a, 2026-11-09)
Q2 b는 "원문 이미지 **핫링크** 또는 언론 이미지로 바꾼다"였다. 시험 결과 **핫링크는 쓸 수 없다**(§3.2). 그래서 실제 선택지는 ② 언론 이미지 또는 ③ 대체 카드였고, 사용자가 **Q3 = a: ②가 되지 않는 건은 대체 카드로 내린다(저장 파일 삭제)** 로 확정했다. 저장본을 그대로 두는 선택지는 쓰지 않는다.
