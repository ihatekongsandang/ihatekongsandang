# 안보 소재 후보 수집기 — 기획서

> 작성: 기획자 (Sonnet 5) · md오더 07 | 작성일: 2026-10-12
> 🔴 **이 도구는 소재 발굴용이며 자동 게시 도구가 아니다.** 후보가 실제 게시물이 되려면 기존 절차(원문 수집 → 보도 대조 → 허용 출처 확인 → 초안 → 리뷰어 게이트/사용자 승인 → 게시)를 그대로 거친다. 이 수집기는 `content/`·`public/`에 아무것도 쓰지 않으며, 코드가 아닌 설계 문서만 이 기획서에 담는다(코드 작성은 금지 — 프로그래머 몫).
> 🔴 저장소 독립 원칙: 본 문서에 다른 서비스명·계정명·사용자 홈 절대경로를 쓰지 않는다. 경로는 상대경로 또는 `$HOME/ihatekongsandang/...`만 쓴다.
> 모든 출처 확인은 **실제 접속 결과**다(`docs/tools/planner-07/check-log.md`에 원문·HTTP 응답·확인 시각 기록). 접속하지 못한 항목은 "확인 필요"로 표기했다.

## 0. 요약

- 실제 접속 확인 결과, **국내 정부·군 기관 4곳(합참·국방부·통일부·국가정보원) 중 RSS·크롤링이 모두 가능한 곳은 통일부뿐**이다. 합참·국방부·국가정보원은 robots.txt가 보도자료 영역을 포함해 거의 전체를 차단하거나(합참·국방부), 아예 전체를 차단한다(국가정보원). 자체 RSS도 없다. 국방부의 경우 과거 정책브리핑(korea.kr) 경유 RSS가 있었으나 **2026-07-01부로 전면 폐지**됐다(저작권 보호 사유, 원문 확인).
- 해외 출처는 38 North·RFA 한국어·연합뉴스 북한 섹션은 RSS가 실제로 동작하고 robots.txt도 허용적이다. **NK News는 robots.txt는 허용적이나 이용약관이 모든 자동 수집을 명시적으로 금지**하고 있어 채택할 수 없다. 미 국방부(현재 명칭 "Department of War", war.gov)·주한미군(usfk.mil)은 Akamai WAF가 단순 HTTP 요청 자체를 차단해(홈페이지조차 403) 이 수집기로는 접근이 어렵다.
- 북한 관영 매체는 직접 접속을 시도하지 않았고(판단 사항), 제3자 아카이브(KCNA Watch)는 이 환경에서 DNS 조회 자체가 실패해 **robots.txt·RSS·약관 전부 확인 필요**로 남겼다.
- **PRD §6① 허용 출처(언론사 보도·수사기관 공식발표·법원 판결문) 기준으로 볼 때, 이번에 조사한 정부·해외 출처 대부분은 "게시물 sources[]에 바로 쓸 수 있는 근거"가 아니라 "소재 발굴 단서"에 그친다.** 구체 분류는 §1 표와 "사용자 결정 필요" 참조.
- AI 요약은 **쓰지 않는 것을 기본값으로 제안**한다(§5). 그 결과 비용은 사실상 0원이며(§9), 수집기는 제목·출처·URL·발행시각·매칭 키워드·수집시각만 저장하는 경량 스크립트로 충분하다.

#### 🔴 사용자 결정 필요 — PRD §6① 개정안 (기획자는 임의로 확정하지 않음)

**질문**: 합참·국방부·통일부(한국 정부부처 공식 보도자료)와 미 국방부·주한미군(외국 정부·군 공식 발표)을 PRD §6①의 허용 출처에 추가할지?

**개정안 문구(안)**: §6① 두 번째 항목을
> "수사기관(검찰·경찰·국가정보원 등) 공식 발표·보도자료, 공개된 법원 판결문"
에서
> "정부기관(검찰·경찰·국가정보원 등 수사기관, 국방부·합동참모본부·통일부 등 소관 부처, 외국 정부·군 공식 발표 포함) 공식 발표·보도자료, 공개된 법원 판결문"
으로 확장하는 안.

**근거**: 안보 소재는 수사기관 발표만으로 다루기 어려운 사안(군사 동향·정책 발표 등)이 많고, 실제로 이런 발표는 이미 언론이 보도하는 1차 취재원이다. 다만 **확장하면 "출처 기반·단정 금지" 원칙의 보호 범위가 넓어져, 정부·군 발표를 그대로 받아쓰는 형태가 늘어날 수 있다**는 반대 고려도 있다(현재는 언론 보도를 거친 내용만 싣게 되어 최소 1단계 검증을 거치는 효과가 있음). 이 트레이드오프는 기획자가 임의로 결정하지 않고 사용자 확정을 받는다.
**확정 전까지 기본 운용**: 위 출처들은 (나)로만 쓴다 — 즉 이 수집기 결과는 슈퍼바이저가 "이 발표를 보도한 언론"을 별도로 찾아 §6①의 등록 언론사 보도로 sources[]를 채우는 절차를 그대로 거친다(기존 `docs/supervisor/photo-post-workflow.md`와 동일한 패턴).

## 2. 수집 방식

- **RSS/공개 API 우선.** HTML 스크래핑은 이번 조사 대상 중 **robots.txt·약관이 명시적으로 허용하는 경우가 없어 전혀 쓰지 않는다**(합참·국방부·국가정보원은 애초에 로봇배제표준으로 막혀 있고, 나머지는 모두 RSS로 충분히 커버됨). 향후 새 출처를 추가할 때도 이 원칙(RSS 없으면 robots.txt·ToS로 스크래핑 허용 여부를 먼저 확인 — 없으면 추가하지 않음)을 유지한다.
- **요청 간격**: 출처당 최소 **10초** 간격(동시에 여러 출처를 돌 때도 순차 처리, 한 출처에 2개 이상 요청을 겹치지 않음).
- **폴링 주기(출처별, §1 "③수집 주기" 참고)**: 통일부·연합뉴스 북한·RFA 한국어는 2~4시간 간격, 38 North는 4시간 간격(갱신 빈도가 상대적으로 낮음). 통일부는 robots.txt의 `Crawl-delay: 5`를 준수한다.
- **하루 호출 상한**: 출처별 **48회/일**(2시간 간격이면 12회라 여유가 크다. 상한은 수동 재실행·장애 복구 시도를 감안한 안전판).
- **User-Agent**: `ihatekongsandang-feed-collector/0.1 (internal, non-commercial monitoring)` — 이 프로젝트 자신의 이름만 포함(저장소 독립 원칙상 다른 서비스명은 쓰지 않음). 연락처(이메일 등)는 넣지 않는다(운영자 익명 원칙).
- **실패·차단 시 재시도/백오프**: 한 폴링 사이클 내 실패 시 **1회만 즉시 재시도**(지수 백오프 불필요 — 폴링 주기가 이미 2~4시간으로 낮은 빈도). 같은 출처가 **연속 3회 폴링 사이클** 실패하면 그 출처를 자동 비활성화(로그에 경고 기록)하고, 사람이 원인을 확인한 뒤 수동으로 재활성화한다. 자동으로 간격을 줄이거나 즉시 재시도를 반복하지 않는다(대량 요청 방지).

- **매칭 범위**: 제목에서 1차 매칭. 제목에 매칭이 없으면 피드 요약(description)에서 2차 매칭하되, 요약 매칭은 §3.4 가중치를 0.7배로 낮춘다(제목 매칭보다 신뢰도가 낮다고 보기 때문).
- **대소문자·띄어쓰기**: 영문 키워드는 대소문자 무시, 단어 경계(word boundary) 매칭(예: "missile"이 "missilennium" 같은 단어 일부에 매칭되지 않도록). 한국어는 공백·구두점을 제거한 뒤 부분 문자열 매칭.
- **제외 컨텍스트 처리**: 키워드가 매칭되어도 같은 제목(요약 매칭이면 요약까지 포함)에 제외어가 함께 있으면 그 후보는 **생성하지 않는다**(저장조차 안 함 — 큐에 쌓이는 노이즈를 줄이기 위함).

### 3.2 중복 제거 규칙

1. **URL 정규화**: 스킴을 `https`로 통일, `www.` 유지(출처별로 다르므로 제거하지 않음), 쿼리스트링 중 추적 파라미터(`utm_*`, `fbclid`, `cp`, `pWise`, `pWiseSub` 등 알려진 패턴)를 제거, 경로 끝 슬래시 통일. 정규화된 URL을 SHA-256 해시한 앞 12자를 후보 `id`로 쓴다(§4) — **같은 URL이 다시 폴링돼도 같은 id가 나와 자동으로 upsert(덮어쓰기)되고 중복 생성되지 않는다.**
2. **같은 사안의 다매체 보도 묶음**: 자동 병합(필드를 합치는 것)은 하지 않는다 — 대신 **클러스터 ID**만 붙여 슈퍼바이저가 한눈에 보게 한다. 두 후보가 아래 조건을 모두 만족하면 같은 클러스터로 묶는다:
   - 발행시각 차이가 24시간 이내
   - 매칭된 키워드 집합이 1개 이상 겹침
   - 제목의 글자 2-그램(bigram) 자카드 유사도가 **0.5 이상**(한국어 조사·어미 차이로 완전 일치하지 않는 경우를 느슨하게 잡기 위한 값. 외부 NLP 라이브러리 없이 순수 문자열 비교로 계산 가능)
   클러스터 내 첫 후보의 `id`를 `clusterId`로 모든 구성원에 기록한다. **삭제·병합은 사람이 한다** — 자동 병합은 정보 손실 위험이 있어 피한다.
3. **기존 게시물과 겹치는 사안 표시**: 후보 생성 시 `content/posts/*.md`의 `tags`를 1회 로드해 두고(폴링마다 읽음, 쓰지 않음), 후보의 매칭 키워드와 겹치는 태그를 가진 기존 게시물이 있으면 `relatedPostIds`에 기록한다(완전 일치가 아니라 참고용 — 최종 판단은 사람).

### 3.3 우선순위 점수

```
priorityScore = sourceWeight × min(keywordWeightSum, 10) × recencyFactor
recencyFactor = 1 / (1 + hoursSincePublished / 24)
```

- `sourceWeight`: 정부·수사기관 공식 발표(통일부 등) = 3, 등록 언론사(연합뉴스 등) = 2, 해외 전문 매체(38 North·RFA) = 1.5, 북한 관영(향후 채택 시) = 0.5(참고용으로 낮게)
- `keywordWeightSum`: 매칭된 키워드별 가중치(예: 간첩·국가보안법 = 3, 도발·미사일·무인기·사이버공격 = 2, NLL·DMZ·탈북 등 = 1, 그 외 기본 = 1)의 합, 최대 10으로 캡
- `recencyFactor`: 발행 후 24시간이면 0.5, 48시간이면 0.33으로 점수가 줄어들어 최신 사안이 자연히 위로 올라온다
- 요약에서만 매칭된 경우 최종 점수에 0.7을 추가로 곱한다(§3.1)

## 4. 후보 1건의 데이터 형식

필드는 제목·출처명·원문 URL·발행시각·매칭 키워드·수집시각만 저장하고, **원문 전문·본문 발췌는 저장하지 않는다**(PRD §5.1 저작권 원칙과 동일 — 후보도 "미리보기" 수준만 가진다). 중복·우선순위 계산에 필요한 최소 파생값(`id`·`priorityScore`·`clusterId`·`status`)만 추가한다.

**형식**: JSONL(한 줄에 하나의 JSON 객체) — 사람이 `grep`·`jq`로 바로 훑어보기 쉽고, 추가·upsert가 한 줄 단위로 단순하다.

**스키마 예시**:
```json
{"id":"a1b2c3d4e5f6","title":"통일부, 북한 도발 관련 입장 발표(예시)","sourceName":"통일부","sourceUrl":"https://unikorea.go.kr/web/unikorea/bbs/.../12345","publishedAt":"2026-10-12T09:00:00+09:00","matchedKeywords":["도발"],"matchedIn":"title","collectedAt":"2026-10-12T11:00:12+09:00","priorityScore":4.5,"clusterId":"a1b2c3d4e5f6","relatedPostIds":[],"status":"new"}
```

| 필드 | 필수 | 설명 |
|---|---|---|
| `id` | ✅ | 정규화 URL의 SHA-256 해시 앞 12자. 안정 키 — URL이 같으면 재폴링돼도 값이 같다 |
| `title` | ✅ | RSS `<title>` 원문 그대로(가공·요약하지 않음) |
| `sourceName` | ✅ | §1 표의 출처명 |
| `sourceUrl` | ✅ | 정규화 전 원문 URL(사람이 클릭해서 열 때는 원본이 필요하므로 정규화 안 한 값을 저장. 정규화는 중복 판정에만 씀) |
| `publishedAt` | ✅ | RSS `<pubDate>`/`<dc:date>` 등 원문 값을 ISO 8601로 변환 |
| `matchedKeywords` | ✅ | 문자열 배열(§3.1) |
| `matchedIn` | ✅ | `"title"` 또는 `"description"`(§3.1·§3.3 가중치 계산용) |
| `collectedAt` | ✅ | 수집 스크립트 실행 시각(ISO 8601) |
| `priorityScore` | 파생값 | §3.3 산출값, 소수 2자리 |
| `clusterId` | 파생값 | §3.2, 묶이지 않으면 자기 자신의 `id` |
| `relatedPostIds` | 파생값 | §3.2, 없으면 빈 배열 |
| `status` | ✅ | `new` / `reviewing` / `published` / `held` / `rejected`(§8) |
| `statusNote` | 선택 | 보류·제외 사유, `published`면 연결된 `content/posts/` id |

## 5. AI 요약 — 쓰지 않는 것을 기본값으로 제안

**결정(기획자 기본값, 사용자 이의 시 변경 가능)**: AI 요약을 쓰지 않는다.

**근거**:
1. 이 큐는 비공개 소재 발굴용이고, 슈퍼바이저가 최종적으로 원문을 직접 열어 확인하는 절차(§8)를 반드시 거친다. 즉 AI 요약이 있어도 없어도 최종 판단은 사람이 원문을 다시 본다 — 중간 요약의 효용이 크지 않다.
2. §4에서 이미 원문 전문을 저장하지 않기로 했는데, AI 요약을 만들면 그 요약 자체가 "원문을 가공한 2차 저작물"이 되어 저작권·정확성 책임이 한 단계 더 생긴다(PRD의 "출처가 뒷받침하는 만큼만 서술" 원칙과 맞추려면 요약을 쓰는 사람이 원문을 검증해야 하는데, 그럴 거면 사람이 직접 제목만 보고 판단하는 것과 차이가 없다).
3. 환각(원문에 없는 내용 추가) 리스크는 "추측 금지" 대전제와 정면으로 충돌한다. RSS 제목만으로도 선별·우선순위에 필요한 정보는 충분하다.
4. 비용이 0에 가까워진다(§9).

**만약 나중에 쓰기로 바뀐다면** 지켜야 할 규칙(참고용으로 남김): 원문에 없는 내용 추가 금지 / 원문 URL이 없거나 열리지 않으면 후보 제외 / "확인된 사실"과 "주장·전망" 구분 표기 / 북한 관영 매체 내용은 "북한 측 주장"으로만 / 요약을 저장한다면 그 저작권·날조 검증 방법을 별도로 정의 / 모델·근거를 명시.

## 6. 저장 위치

**결정: 로컬 전용(.gitignore), 공개 레포에 커밋하지 않는다.**

**근거**:

- 업로더(반공-업로더)·슈퍼바이저가 같은 작업 폴더(`$HOME/ihatekongsandang`)를 쓰므로, 로컬 파일시스템에만 두어도 두 세션 모두 접근 가능하다(git으로 공유할 필요가 없다).

**경로(제안, 최종 경로는 프로그래머가 구현 시 확정)**: `$HOME/ihatekongsandang/data/security-feed/queue.jsonl` — 프로젝트 루트 안에 두되 `.gitignore`에 `data/security-feed/`를 추가한다(이 추가 자체는 프로그래머 구현 단계에서 수행 — 기획자는 코드·설정 파일을 수정하지 않는다).

**보존 기간·정리 규칙**:
- `status: published` 또는 `status: rejected`인 항목은 **90일** 보관 후 자동 삭제한다(`collectedAt` 기준). 삭제 전 월별 요약 로그(건수·출처별 집계)만 `data/security-feed/archive-log.txt`에 한 줄 남긴다(원문 데이터는 남기지 않음).
- `status: new` 또는 `reviewing`인 항목은 기간 제한 없이 유지한다(사람이 처리할 때까지).
- `status: held`는 기존 `docs/supervisor/drafts/2026-09-28-held-recheck.md` 패턴과 동일하게 재확인 대상이므로 90일 규칙에서 제외하고 무기한 보관한다(단, 이월 재확인 시 다시 열어 본다는 CLAUDE.md §8 원칙을 그대로 적용).

## 7. 실행 환경

- **예약 실행**: macOS 로컬 환경(`launchd`, `StartInterval`로 §2의 폴링 주기를 초 단위로 지정). `cron`도 대안이나 macOS 권장 방식은 launchd다. 실제 `.plist` 작성은 프로그래머 구현 단계.
- **런타임**: Python 3(표준 라이브러리만 — `urllib.request`, `xml.etree.ElementTree`, `hashlib`, `json`)을 제안한다. macOS에 기본 설치되어 있어 **추가 의존성 설치가 전혀 필요 없다.** (대안으로 Node.js의 내장 `fetch`를 쓸 수도 있으나, 이 프로젝트의 Next.js 의존성 트리와 분리된 독립 스크립트로 두는 것이 "가벼운 단일 스크립트" 요구사항에 더 맞는다 — 최종 언어 선택은 프로그래머 판단.)
- **메모리 사용 목표**: 1회 실행(폴링 1 사이클)당 **100MB 이하**. RSS 피드 몇 개를 내려받아 파싱하고 JSONL 파일을 읽고 쓰는 수준의 경량 작업이라 이 목표는 넉넉하다.
- **절대경로·개인정보 금지**: 스크립트 안에 `$HOME` 절대경로·전화번호·계정명을 하드코딩하지 않는다. 데이터 디렉터리 경로는 환경변수(예: `SECURITY_FEED_DATA_DIR`)로 받고, 기본값은 스크립트 실행 위치 기준 상대경로로 둔다. 통일부 Open API를 쓰게 되면 그 API 키도 환경변수(예: `UNIKOREA_API_KEY`)로만 받는다.
- **실행 로그**: `data/security-feed/run.log`(위 데이터 디렉터리와 같은 위치, 역시 `.gitignore` 대상)에 사이클마다 한 줄(시각·출처별 성공/실패·신규 후보 수)을 남긴다.
- **실패 알림**: 사용자 개인 연락처(전화·이메일 등)를 코드에 넣지 않는다. 필요하다면 방식만 설계해 둔다 — 예를 들어 `docs/triggers/`에 실패 표시 파일을 만들어 슈퍼바이저 세션이 다음 가동 시 발견하게 하는 방식(이미 이 프로젝트의 트리거 파일 관행과 동일한 패턴). 실제 알림 구현은 프로그래머 판단.

## 8. 슈퍼바이저 사용 흐름

### 8.1 "안보 소재 뭐 있어?" 질의 응답 절차
1. 슈퍼바이저가 `data/security-feed/queue.jsonl`을 읽는다.
2. `status: new`인 항목만 `priorityScore` 내림차순으로 정렬, **최대 10건**을 보고한다(그 이상이면 "외 N건 더 있음"으로 안내).
3. 보고 양식(건별): 제목 · 출처명 · 발행시각 · 매칭 키워드 · 우선순위 점수 · 원문 링크 · (있으면) `relatedPostIds`로 연결된 기존 게시물.
4. 클러스터(같은 `clusterId`)로 묶인 항목은 대표 1건만 상단에 보이고 "+N건 같은 사안"으로 축약 표시한다.

### 8.2 후보 → 게시 초안 전환 절차
1. 사용자가 특정 후보를 지정해 "게시해 보자"고 하면, 슈퍼바이저가 queue.jsonl의 해당 항목 `status`를 `reviewing`으로 갱신한다.
2. 원문 URL을 **반공-업로더**(사용자가 보내는 URL 게시 전담 — `docs/handoffs/supervisor-2026-10-01-session-handoff.md` "세션 역할 분담" 참조)에게 넘긴다. 이후 절차는 기존 `docs/poster/guide.md`·PRD §6②③과 완전히 동일하다 — 원문 수집 → 보도 대조(§1의 "(가)/(나)" 분류에 따라 sources[]에 바로 못 쓰는 출처는 별도의 등록 언론사 보도를 찾아야 함) → 허용 출처 재확인(PRD §6①) → 게시/병합/보류/게시불가 판단 → 한·영 작성 → 검증 → 커밋.
3. 업로더의 완료 보고(트리거·핸드오프)를 슈퍼바이저가 확인한 뒤, queue.jsonl의 해당 항목을 **슈퍼바이저만** 갱신한다(업로더는 queue.jsonl을 직접 건드리지 않는다 — 두 세션이 같은 파일을 동시에 고치는 충돌을 피하기 위함, 기존 "각자 자기 파일만" 원칙과 동일한 정신):
   - 게시됨 → `status: published`, `statusNote`에 `content/posts/{id}` 기록
   - 병합됨 → `status: published`, `statusNote`에 병합된 기존 게시물 id 기록
   - 보류 → `status: held`, `statusNote`에 보류 사유
   - 게시 불가 → `status: rejected`, `statusNote`에 사유(허용 출처 0건·오탐·중복 등)

### 8.3 상태값
`new`(신규, 아직 아무도 안 봄) → `reviewing`(검토중, 업로더에게 넘어감) → `published`/`held`/`rejected`(종결). 되돌리는 경우(예: `held`였다가 나중에 근거가 생겨 게시)는 수동으로 `new`로 되돌린 뒤 §8.2를 다시 거친다.

## 9. 비용·리소스 사전 추정

**가정(명시)**:
- 실제 채택 가능 출처(§1에서 robots·약관·RSS 모두 확인된 것): 통일부·연합뉴스 북한·38 North·RFA 한국어 **4곳**. (미 국방부는 ToS 확인 필요라 보류, NK News는 제외, 정부기관 3곳은 애초에 RSS/크롤링 불가.)
- 폴링 주기: §2 기준 평균 3시간 간격(1일 8회)으로 가정.

**하루 호출 수**:
```
하루 호출 수 = 출처 수 × 1일 폴링 횟수 = 4 × 8 = 32회/일
```
이는 §2의 출처별 상한(48회/일)보다 낮아 여유가 있다.

**AI 요약 비용**: §5 결정(쓰지 않음)에 따라 **0원**.

**AI 요약을 쓸 경우의 참고 계산식(§5가 뒤집힐 때를 대비, 가정 명시)**:
```
일일 토큰 비용 = 신규 후보 수 × (입력 토큰 수 × 입력 단가 + 출력 토큰 수 × 출력 단가)
```
- 가정: 하루 신규 후보 20건(가정), 입력 400자 내외(제목+피드 요약, 원문 본문 아님)·출력 150자 내외(가정)
- 모델별 실제 단가는 수시로 바뀌므로 **이 기획서 작성 시점 기준 가격을 확인하지 못했다 — 확인 필요**(채택 시점에 다시 조회해 반영). 다만 이 규모(건당 수백 자)는 어떤 모델을 쓰더라도 월 비용이 체감상 크지 않을 구간이라는 점만 참고로 적는다(확정 수치 아님).

**인프라 비용**: 로컬 launchd 실행이라 별도 서버·클라우드 비용 없음. 공공데이터포털(통일부) API 키 발급은 무료(일반적인 공공데이터포털 운영 방식 — 이번에 유료 여부를 별도로 재확인하지는 않았음, 기존에 알려진 바와 다르면 **확인 필요**).
